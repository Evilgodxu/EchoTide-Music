基准测试
一个残留观察（未处理）：`home_landscape_mode` 偶发 MISS，因为它位于自动隐藏的顶栏，而`revealTopBar()` 是坐标点击，唤出时机不稳。

打包整型输出无法嫁接在 media3 的默认音频输出上（已核实，勿再尝试）

背景：部分机型的 USB 动态混音端口只声明打包整型：较早的一批只声明 24 位（PCM_24BIT_PACKED），
部分 USB 耳放/解码器（如 KT02H20）只声明 32 位整型（PCM_32BIT），两者直出要成立都得写出该编码；
而 media3 的 DefaultAudioSink 只产出浮点与 16 位整型。曾按「改写 AudioOutputProvider 给出的输出编码、
在 AudioOutput 层转换字节」实现，结果是启用直出即播放崩溃（BufferUnderflowException → 播放错误），
且两次崩溃点完全相同。原因如下，三条互相封死了轻量方案：

1. DefaultAudioSink 会把管线缓冲与所声明的输出编码一并交给音量渐入：
   setOutputBuffer → maybeRampUpVolume → PcmAudioUtil.rampUpVolume(buffer, outputConfig.encoding, …)。
   渐入只在开头约 200ms 内生效（writtenFrames < rampFrameCount），此时按 24 位步长读浮点缓冲即越界。
   声明编码与实际数据不符，是崩溃的直接原因。
2. 让声明编码与数据一致（都保持浮点）也不行：AudioTrackAudioOutput.pcmFrameSize 取自 config.encoding，
   会按浮点算出 8 字节/帧，而 24 位整型轨道实际每帧 6 字节，位置与欠载记账会差三分之一。
3. 唯一自洽的做法是让管线真的产出目标位深，但用户处理器链只挂在整型分支：
   整型分支会先经 ToInt16PcmAudioProcessor 把高分辨率源截成 16 位；浮点分支（高分辨率源走这条）不挂用户链、
   无从注入。故高分辨率源无论走哪条分支都得不到打包整型写出。

结论：要在只声明打包整型的设备上做直出，只能另起一个输出实现，不能在媒体3 的默认输出上嫁接。
现由 IntPcmAudioSink 承担：它自行按所设位深（24 位或 32 位）建轨，再交给媒体3 的 AudioTrackAudioOutput
托管（位置、欠载、变速、音量、音效都复用该实现，本层只做「接受解码数据—转成整型帧—写出」）。
两种位深共用一份实现，由 PerDeviceAudioSink 各持一个实例，按设备声明的条目切换。
与默认输出的差别：不裁剪编码器延迟与填充（曲目间隙略长），不支持静音跳过与隧道。
走不通的那版嫁接实现留档于 Temporary Test Resources/int24-回退存档，仅作记录。

不再事前建轨实测「能不能写出」（已核实，勿再引入）

打包整型是否只被少数机型受理、且没有能力查询接口——曾经据此写过一个「实际建一次探测轨道再释放」的
可用性实测（IntPcmOutputSupport），现已**整体删除**。两次实证都指向同一结论：

- 探测的结论取决于**探测时所处的现场**，与真正建轨时不一致，因此不可作为判据（同一档位在设备尚无输出
  时探测失败、起播有输出后探测通过）；
- 探测本身会把设备拖进坏状态：实测（KT02H20，Xiaomi 2107119DC / Android 14）在一次探测之后，**连 44100
  的浮点轨都建不起来**，播放随即以 ERROR_CODE_AUDIO_TRACK_INIT_FAILED 终止；探测还会按设备声明把 24 位、
  32 位逐档建一遍，而这些档位根本不在候选里（纯属白建轨）。

故现在的口径：

1. **「能不能写出」不再事前判定。** 候选只按「本应用写得出的编码」（writablePcmEncodings：16 位、浮点、
   打包整型）与设备**声明**的条目筛出，不做任何建轨试探——既不乱建档位，也不会拖坏设备。
2. **真正的判据只有两个，都在真实链路上：** 系统是否受理该混音器属性（setPreferredMixerAttributes 的
   返回值），以及音频轨是否真的建得起来。后者失败时由音频输出侧逐档降级兜底（见下条），不再把责任推给
   事前推断。
3. 已被证伪建不出音频轨的格式按会话、按设备记入不可用（UsbDirectOutput.unrealizableFormats），换设备即
   作废——避免同一失败被反复重试，也避免把某一台设备的坏档位记到新设备头上。

同理，被系统拒绝的混音器属性也不记成「已下发」：记下来会让同一条属性在之后的换曲里再不被重试。
判定「已受理」与抑制重复下发共用同一份状态（acceptedMixerAttributes），不接受「下发过」与「已受理」两本账。

动态混音端口查询会对「没有输出」的设备给空表（已核实，勿把空表当终局）

getSupportedMixerAttributes 不经 AudioService，而是 AudioManager 直查音频策略的原生接口；Java 层把任何
非 SUCCESS 一律折成空表，所以**空表有两种含义**：厂商没声明动态混音端口，或该设备此刻没有输出（平台按
输出端口应答）。实测同一台 KT02H20：应用未起播时查询得空表，起播后同一设备返回 7 条档位。

故「未声明动态混音端口」只能当作**当下这次问不到**，两道措施缺一不可：

1. **每次音频轨建成后重问一次**（UsbDirectOutput.onOutputEstablished，由音频输出的「音频轨已建立」回调
   驱动）。踩过的坑：开关在未起播时打开 → 空表 → 判定设备不支持 → 随后起播，输出已建成却没人再问，
   直出再也没回来（现象：受支持的源采样率也一直走混音，手动换曲同样无效）。
2. **问不到时沿用上次问到的声明**（UsbDirectOutput.declaredFormats，按设备编号归属）。厂商声明的档位是
   设备的固定属性，不随「此刻有没有输出」变化，所以空表对判定毫无信息量。只做第 1 条不够：实测一次
   「撤销直出」之后就再也回不来——撤销会一并解除路由钉定，此后新起的输出不再落在该设备上，查询于是
   每次都得到空表，第 1 条的重问也全都落在空表上（现象：末几首一路系统混音，且日志里连一条候选下发都没有）。

另一处必须成对：路由若在曲中才成立，写出变体不会自己跟上（变体只在音频输出重配点决策），故成色回调里
同时补一次重配（PerDeviceAudioSink.syncRouting，投回音频线程、变体未变则跳过）。少了它，状态会显示
「源格式直出」而音频轨仍以浮点写出——格式与偏好不符，AudioFlinger 静默混音，名不副实。

位完美是「请求」，不能替厂商声明（已核实，勿在 UI 上冒充）

MIXER_BEHAVIOR_BIT_PERFECT 只是一条请求：平台按设备动态输出 profile 声明过的行为应答——
getSupportedMixerAttributes 返回的即「可用的集合」（官方 setPreferredMixerAttributes 文档要求先查它），
声明里没有该行为的档位会被拒。行为由 profile 的 AUDIO_OUTPUT_FLAG_BIT_PERFECT 反推，而国产厂商的 USB
声卡普遍不声明它（实测已知两台：一台只声明 24 位整型，一台只声明 32 位整型，均只有默认行为）。

因此：
1. 应用**不能**把默认行为条目当作「设备已声明位完美」上报成色——默认行为的流仍经混音（只是采样率与源
   一致），把它显示成位完美正是「以已直出之名走混音路径」的翻版。成色只按平台实际受理的行为给。
2. 但可以**先试后回落**：挑到默认行为条目时，按同一格式再请求一次位完美（UsbDirectOutput.applyMixerAttributes），
   受理即得位完美、被拒则回落默认行为（源格式直出）。试的成本是一次可能被拒的下发——被拒不建立任何东西，
   而它换来的是「厂商漏标但框架受理」这一种可能，以及日志里一条明确结论（受理 / 拒绝）。
3. 真正绕开混音的另有一条路（AAudio 独占/MMAP，数据直写驱动），但它要求 HAL 声明 MMAP 支持，且需要
   另写一套输出实现（时钟、位置、欠载都得自管），与 media3 的音频输出体系不兼容，不在当前范围内。

受理混音器属性 ≠ 本应用真的用得上它（已核实，勿以受理为终局）

setPreferredMixerAttributes 的受理只说明设备侧存在匹配的动态输出 profile，**不说明本应用建得起与之
逐字段一致的音频轨、更不说明写得出去**。同一台机（KT02H20，Xiaomi 2107119DC / Android 14）两处都实测过：

- 位完美请求被拒后改按默认行为下发「48000Hz/2ch/24 位整型」，系统受理并进入「源格式直出」，随后
  IntPcmAudioSink 建轨抛 UnsupportedOperationException: Cannot create AudioTrack——AOSP 里该裸消息只出自
  Builder.build() 的「原生建轨失败、轨道停在 STATE_UNINITIALIZED」一处（AudioTrack.java:1563-1567），
  不是 Java 参数问题；该异常随 ERROR_CODE_AUDIO_TRACK_INIT_FAILED 终止了整曲播放。
- 另一档 24 位轨**建得起来、写不出去**：轨道建成后 write 返回 AudioTrack.ERROR_INVALID_OPERATION(-3)，
  播放随 ERROR_CODE_AUDIO_TRACK_WRITE_FAILED 终止。该错误码不在媒体3 的可恢复集（只有 ERROR_DEAD_OBJECT
  算可恢复），所以它会直接带走整曲播放，而不是交给渲染器重试。

三条结论：

1. **事前推断拦不住它，也不该去做。** 唯一的判据是真实建轨与真实写出；事前实测的结论取决于当时的现场，
   且探测本身会把设备拖坏（见上条）。
2. **唯一可靠的拦截点是 sink。** 生效变体建不起音频轨、或建起后写不出，都必须逐档降级：
   PerDeviceAudioSink 捕获 InitializationException 与 WriteException（后者只取不可恢复的一支），
   通知直出把该格式记为不可用并改挂下一档，本次缓冲续写；全部用尽才交**可恢复**错误（不以不可恢复错误
   终止播放）。直出是尽力而为，任何一环失败都不该把整曲播放带走。
3. **降级次序由直出按候选表续试得出，不用固定次序表。** 候选表是「源格式在前、设备声明的条目在后」，
   故次序正是设计的那条——先源格式，失败后退回设备声明的位深与采样率，设备侧也无档位可用才回系统混音。
   固定次序表（曾为 FLOAT → INT16 → INT24 → INT32）做不到这一点：它不知道设备声明了哪些位深，
   从 24 位失败会先跳到浮点、绕一圈才回到设备声明的档位。
   **续试在撤销之前做**：setPreferredMixerAttributes 是覆盖式的，改挂成功即无需撤销，设备也不会被解钉；
   撤销会把设备解钉、成色落回系统混音（免打扰白翻一次），并触发上一条那个「再也回不来」的死结。
   改挂不成才撤销——那条失败格式的偏好此刻仍挂着，不清掉 AudioFlinger 会继续静默混音。

   缓冲区间的处理两边不同，别混：建轨失败发生在对本缓冲的任何读写之前，可直接改交下一个变体；
   写出失败时缓冲可能已被消费（媒体3 的输出实现会就地消费输入缓冲），故统一退回本轮的缓冲起点再重试。
   失败的一方已随切换被释放，它接纳而未播出的数据不会再播出，整块重写才是连续的。
4. **该机的 24 位整型整档不可用，而设备声明的 32 位档位可用**：44100/24 被拒（根本构不成候选）、
   48000/24 被受理但建轨抛异常、96000/24 被受理但写出失败。24 位源落到 32 位是逐位无损的（左移补零），
   故「源格式 24 位失败 → 退回设备声明的 32 位」正是所要的降级，也才是 24 位源能直出的唯一途径。
   记为不可用的格式按会话排除（UsbDirectOutput.unrealizableFormats），换设备即清零。
   排除按**格式**（采样率+声道+编码）而非按编码：档位的可用性档位相关，本机上 16 位整型就是
   48000 被拒而其它档位可用——把「48kHz/24 位」的失败一概记到 24 位整型头上会白放弃一个可能可用的档位。
   代价是每换一个新采样率都会再试一次 24 位、再失败一次并降级（实测 48000 与 96000 各一次）。

解码输出的位深随源位深收窄（已核实，勿再无条件索取浮点）

媒体3 只在**恰好**收到 `SINK_FORMAT_SUPPORTED_DIRECTLY` 时才向解码器索取浮点输出
（MediaCodecAudioRenderer 据此设 KEY_PCM_ENCODING），故「能力基准恒报浮点可直出」会让**所有源**（含 16 位）
都被解成 32 位浮点——面板的「解码输出」一栏因此与源对不上，写出也要多走一次转换。

现按源位深收窄（PerDeviceAudioSink.formatSupportWithSourceBitDepth）：已知源为 **16 位及以下**时改答
「需转换」，解码输出即落在源位深上（与写出、面板一致）；**位深未知或高于 16 位**时照旧报浮点——无损源
的 24/32 位精度不能丢，位深尚未读到的竞态也按高分辨率处理，宁可保精度不误降。

这条收窄的取值有**时机**要求，漏掉就会把「收窄」用反（实测：24 位源被 16 位解码，随后按 24 位建轨）：

- **取值必须属于当前曲目**（MusicPlaybackState.currentSourceBitDepth 按曲目归属过滤）。切曲瞬间记录仍是
  上一首的，直接取用会把上一首的位深当成这一首的源位深；归属不符要当作「没读到」而不是回退取值，
  两侧含义相反——「没读到」照旧报浮点，「已知为 16 位」才收窄。
- **必须在解码器配置前落定。** 申报发生在解码器配置那一刻，早于解码头格式回调，也早于应用收到轨道回调；
  而源格式是异步读来的，故起播前先按容器头读一次位深与声道（MusicPlaybackState.
  recordSourceBitDepthBeforePlayback，切歌入口与自动接续两处都调）。只读容器头、不读采样率与比特率，
  后两项不是申报依据。


输出采样率的两层口径（已核实，勿再混谈）

一处反复出现的分歧：说「本应用不协商采样率」还是「采样率跟着设备支持在走」，两者都对——答的是不同的问题。

1. 谁做的调整：本应用不重采样，也不为迁就设备挑采样率。候选只有两档——先按源格式直接构造并请求，被系统
   拒绝后再从设备声明的动态混音端口条目里挑；两档都要求采样率、声道与编码逐字段相符，不做「挑最接近条目」
   的退让；两档都挑不出即整体让位，输出路由与混音器属性一并撤销。先试源格式是为设备只上报上限的情形
   （编码只报最高的 32 位或 24 位、采样率只报高采样率）：按声明挑选会漏掉本可直出的低档位（典型如 44.1kHz/16 位）。
2. 最终落在哪一档：输出采样率始终落在设备支持的那一档。直出成立时，设备支持的正是源采样率，故输出即源采样率、
   数据不被改动；直出不成立时由系统混音器把源重采样到设备的采样率——AudioInfoCollector.outputSampleRate
   此时读的是设备的 PROPERTY_OUTPUT_SAMPLE_RATE，与源不等即在音频信息面板标为已重采样。

故「动态适应设备」作为结果描述成立，「本应用不协商采样率」作为机制描述也成立；把二者说成互相否定的，都是只读了一层。
副标题取的是结果口径。

系统导航栏（虚拟按键）适配（已核实，勿只留一处）

「虚拟按键压在播放控制按钮上」不是布局写错，而是两件事叠加：三键导航栏默认带一层系统铺的不透明底色，
且 edge-to-edge 下底部偏移被取消、内容默认延伸到导航栏后面。下面几点共同构成适配，删掉任一点都会退回原状：

1. `MainActivity` 在 `enableEdgeToEdge` 之后必须显式 `window.isNavigationBarContrastEnforced = false`。
   只靠 `enableEdgeToEdge` 拿不到全透明导航栏：其默认 `navigationBarStyle` 为 `auto`，而 `auto`
   会打开强制对比度（API 29+ 由 androidx 设 true，API 35+ 平台默认即 true），三键导航栏被铺上不透明底色。
   `auto` 与 `light/dark` 的差别就在这个属性，与传入的 scrim 颜色无关。
2. 首页竖屏与横屏一并全沉浸：`isHomePortraitImmersive` 同样走 `HIDE_ALL`，首页（含在线搜索页、歌单页）
   隐藏状态栏与导航栏两条。沉浸只下发隐藏、不裁剪布局——上滑临时唤出的系统栏以覆盖方式呈现，
   不改变 insets，故界面侧不必为它做避让。
3. 仍显示系统栏的页面（设置/排版/频谱/存储管理/元数据）各自避让导航栏高度，无一处统一兜底：
   滚动页把避让加在滚动容器上（`navigationBarsPadding`，见 `CacheGroups` 原注释）；
   带键盘的页一律取 `WindowInsets.ime.union(navigationBars)`（元数据编辑页）——键盘展开时其高度
   已含导航栏区域，直接叠加会让出两段高度。
4. 首页的避让分两类。搜索页与歌单页列表在沉浸态下取值恒为 0，保留并非冗余：导航栏被外部原因
   显示出来时（独立窗口、切页过渡、ROM 不认隐藏请求）仍能保证底部控件不被压住。
   竖屏播放页的 `bottomClearance` 则取固定留白 `BottomBarClearance`（24dp）与导航栏高度的较大值，
   沉浸态下不为 0 —— 底部留白由该固定值决定，而不是由「屏幕高宽差减去内容高度」的余量决定；
   后者随屏幕尺寸与高宽比漂移，同一套布局在不同机型上会忽高忽低。竖屏播放页的高度分配也不再用
   手工估算的内容高度：封面、歌词组、信息/控制组三组之间由 `Arrangement.SpaceBetween` 分配，
   封面为 `weight(1f, fill = false) + heightIn(max = 全宽正方形)`（保留正方形、窗口过矮时收缩），
   富余空间只落入封面↔歌词、歌词↔歌曲信息两处，把歌词组夹在中间均分，内容高度交由系统实测。
   两个底部弹层（播放列表、音频信息）是例外，不避让导航栏：面板底色
   铺到屏幕底缘，在面板根节点预留这段高度只会在底部留下一条与底色同色、不随内容滚动的色带，
   与「元数据编辑页去掉固定底部内边距」是同类问题；面板自身的底部内边距同理取消，只留左右与顶部。
   播放列表弹层仍避让键盘（`imePadding`）——键盘自身已覆盖导航栏区域，无需再叠加导航栏高度。
5. 图标颜色按「图标底下压着什么」定色：首页是深色封面衍生背景，故固定白色（`HomeScreen` 的 `SideEffect`），
   弹层展开时改回按主题取色；其余页面由 `StatusBarStyleEffect` 统一声明。


播放模式新增枚举值只能追加在末尾（已核实，勿再调整顺序）

`PlayMode` 的序号以 ordinal 落盘（`music_saved_mode` 与播放状态快照的 `mode` 字段各一份），
读取时按 `PlayMode.entries.getOrElse(savedMode)` 还原。**在中间插入新值会让已装机用户保存的序号
整体错位** —— 保存的 1 原意是 RepeatAll，插入后会被解析成它前面那个值。新增模式一律追加在末尾，
心动模式（`Highlight`）即按此追加。

心动模式的片段播放不得计入完整播放（已核实，勿放开）

心动模式播的是 30–45 秒的副歌片段，若照常计入 `recordPlayed`，会同时坏掉两处：

1. 常听（`recentPlayedIds`，3 天内播够 2 次）会把每首都收进来，常听歌单失去意义；
2. `PlaylistSort` 等按播放记录排序的路径随之失真。

故 `recordPlayed` 的两个调用点（`onMediaItemTransition` 与 `STATE_ENDED`）都以
`playMode != PlayMode.Highlight` 为前提。裁剪后片段的结束由播放器按「自然播完」上报，
不加这道闸就会静默计入。


心动模式的片段一律取自持久化表（已核实，勿改回播放时解析）

片段的「算」与「用」必须是分开的两段：

- **算**：`HighlightScanner` 在后台成批扫描全库，结果连同「歌词 + 时长 + 算法版本指纹」由
  `HighlightStore` 落盘。指纹未变不重算；歌词补齐、时长补全或算法升级后指纹改变，自动重扫。
  启动恢复完成、曲库变化、启用心动模式三处触发。歌词此刻取不到的曲目记为 `Unresolved`
  而**不是** `NoChorus` —— 前者只是数据未就绪，据此跳过会让歌词尚未补齐的曲库被整库跳过；
  后者才是真的没有高潮段，只有它才跳过该曲。
- **用**：播放路径只做一次内存查表（`HighlightStore.segmentOf`）。切歌、切模式都不读盘、不定位。

历史上曾在播放路径上按需解析（切歌时读歌词并定位，再逐项替换队列里的 MediaItem 补片段）。
那条路有三个必然的毛病，故不要再改回去：每次切歌都要读盘与计算；片段何时生效取决于歌词何时就绪，
行为不确定（表现为「开了模式却没有片段」）；切换模式要逐项替换队列，队列长时明显卡顿。
还有一个隐蔽的坑：当时的队列一致性判定只比 mediaId 与 URI，看不见裁剪差异，新构建的「带片段的项」
会被判成「队列没变」而跳过装载。现在整队列按片段表一次性重建，`sameQueue` 里保留裁剪区间比较作兜底。

模式切换对当前曲目立即生效（进入自片段起点起播、退出还原到整曲的绝对位置），不是「从下一曲才开始」。
因此落盘的播放位置必须是**整曲的绝对位置**（见 `persistablePositionMs`）：控制器回报的是片段内进度，
直接落盘会让恢复时对不上；恢复由 `mapSavedResumePosition` 换算回片段坐标系，两个方向对称。

片段的收尾一律落在**歌词行的边界**上（见 `HighlightLocator`）：先纳入整个副歌块，
再逐行补到时长下限，上限用「再补一行就会超出」判定，于是最后一行总能唱完，
而不是被 45 秒硬切在半句上。块自身就长过上限时**必须向回收缩**到 45 秒以内，不得把整块原样返回。
收尾另取「下一行起点」与「末字演唱终点」的较大者：逐字歌词的末字可能唱到下一行起点之后，
只认下一行起点会把这一行截断，这正是「末句没唱完就被切走」的成因。



心动模式只做纯歌词分析，不解码音频（已核实，勿改回音频精修）

副歌定位（`HighlightLocator`）只用歌词文本与时间戳，分四步：

- **重复结构**定候选：副歌在歌词上表现为同一批行反复出现，这是 RefraiD、pychorus 一类副歌检测的
  共同前提（副歌是整曲重复次数最多的段落）。只出现一次的行块不成候选；制作信息行（作词/作曲……）
  复用 `LyricFeatures.cleanLyrics` 的同一套前缀判据剔除，避免整段重复的信息行被判成副歌。
- **位置、时长、密度、停顿、结尾权重**给候选打分：首现越晚、时长越贴合 30–45 秒、片段内行越密
  （每秒行数越多）、行间最大间隔越短、越靠近曲末的块越像副歌。
- **取最后一遍完整副歌**：每个候选只收其最后一次能成段的出现 —— 末遍副歌通常是全曲落点，
  且收尾落在歌词行边界上；末遍短到收不出片段时退回上一遍。
- **不取歌词行数少的片段**：候选按片段内行数降序排列，行数相同再比得分，于是「高潮必是 30–45 秒内
  歌词行数最多的一段」直接落在排序首位，稀疏段落自然落选。

**为什么不做音频**：逐曲解码全曲能量（`MediaCodec` 解 PCM、逐帧求响度与高频占比）在整库扫描上
代价偏大，对「有清晰重复副歌」的绝大多数流行歌并不提供额外信息；而把精修推迟到进入模式时才做，
又让片段何时生效依赖扫描时机，行为不确定。改为纯歌词后，扫描只读歌词与时间戳，代价低且与当前
模式无关。为此 `EnergyEnvelope` / `HighlightSelector`（音频兜底与响度谷吸附）连同条目上的
`refined` 标记一并移除；算法版本升至 `v4`，旧结果按指纹整体作废重算。

「有歌词却乱播或漏播」的两个来源据此封死：乱播（把重复的主歌当副歌）靠「行数最多 + 五项打分」纠正；
漏播（歌词无时间轴）判为 `Unresolved` 退回整曲播放，**只有「有可用歌词时间轴 + 确实收不出片段」
才判 `NoChorus` 跳过该曲**，歌词尚未补齐的曲库不会被整库跳过。


心动模式下两套时间坐标不得混用（已核实，勿凭直觉取用）

播放器回报的位置以**片段起点为原点**，而歌词行的时间戳是曲目内的**绝对时间**。
两者只允许在状态层换算，各消费点按用途取值：

- **歌词一律取绝对时间**：`MusicPlaybackState.lyricPositionMs`（= `livePositionMs` + `highlightPositionOffsetMs`）。
  竖屏歌词的跟随锚点、悬浮窗迷你播放器、长按歌词定格编辑目标行，三处都取它。
  它们曾直接读 `livePositionMs`，于是心动模式下整段歌词落后一个片段起点 —— 这就是
  「歌词没跟随片段」的成因。
- **进度条取片段相对时间**：`currentPosition` / `duration` 原样使用，它要的正是「这一段播了多少」。
  显示成 0:12 / 0:40 而非 1:22 / 4:05 是有意的。
- **以歌词行为目标的跳转必须换算**：歌词行给的是绝对时间，`seekTo` 的目标必须是片段坐标系，
  经 `toPlayerPosition` 换算；不换算会落到片段之外被播放器钳到边界。
- **落盘与恢复的坐标**：落盘存整曲绝对位置（`persistablePositionMs`），
  恢复经 `mapSavedResumePosition` 换回片段坐标系。

新增任何读播放位置的界面时，先问一句：我要的是「这一段里的进度」还是「整曲里的时间」。


心动模式与音频直出互斥（已核实，勿放开）

USB 直出（`AudioOutputMode.BIT_PERFECT` / `FORMAT_LOCKED`）成立时必须退出心动模式，且直出期间不接受
再进入：位完美一档绕过系统混音，**音量与音效都不生效**，而心动模式片段首尾的淡入淡出正是靠
`Player.volume` 做的（见下条），在直出链路上无从实施。直出本身也为整曲保真聆听服务，与「把每首裁成
30–45 秒片段」取向相斥。判定以**实际输出成色**为准，不看设置开关 —— 开关打开而设备不支撑时播放仍走
系统混音，此时心动模式照常可用。

片段首尾的淡入淡出靠降低播放器音量实现，不进音频数据

片段由裁剪（`ClippingConfiguration`）切开，首尾都是硬切；`MusicPlaybackState.syncHighlightFadeVolume`
在片段开头把 `Player.volume` 由 0 升到 1、在结尾前由 1 降到 0，掩掉突兀的进出。位置与时长都取控制器
对当前项的回报（裁剪后即以片段为原点）。要点：

- **只对确有片段的曲目生效**：心动模式下没有片段的曲目照常整曲播放，不该被从头淡入到尾。
- **片段播放期间进度轮询加密到 40ms**：200ms 的台阶会让斜坡听成几次跳变；非片段播放仍为 200ms。
- **退出心动模式须即刻把音量复位到 1**：否则淡出末尾的低音量会被整曲播放沿用。
