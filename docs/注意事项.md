打包整型输出无法嫁接在 media3 的默认音频输出上（已核实，勿再尝试）

背景：部分机型的 USB 动态混音端口只声明打包整型：较早的一批只声明 24 位（PCM_24BIT_PACKED），
部分 USB 耳放/解码器（如 KT02H20）只声明 32 位整型（PCM_32BIT），两者直出要成立都得写出该编码；
而 media3 的 DefaultAudioSink 只产出浮点与 16 位整型。曾按「改写 AudioOutputProvider 给出的输出编码、
在 AudioOutput 层转换字节」实现，结果是启用直出即播放崩溃（BufferUnderflowException → 播放错误），
且两次崩溃点完全相同。原因如下，三条互相封死了轻量方案：

1. DefaultAudioSink 会把管线缓冲与所声明的输出编码一并交给音量渐入：
   setOutputBuffer → maybeRampUpVolume → PcmAudioUtil.rampUpVolume(buffer, outputConfig.encoding, …)。
   渐入只在开头约 200ms 内生效（writtenFrames < rampFrameCount），此时按 24 位步长读浮点缓冲即越界。
   声明编码与实际数据不符，是崩溃的直接原因。
2. 让声明编码与数据一致（都保持浮点）也不行：AudioTrackAudioOutput.pcmFrameSize 取自 config.encoding，
   会按浮点算出 8 字节/帧，而 24 位整型轨道实际每帧 6 字节，位置与欠载记账会差三分之一。
3. 唯一自洽的做法是让管线真的产出目标位深，但用户处理器链只挂在整型分支：
   整型分支会先经 ToInt16PcmAudioProcessor 把高分辨率源截成 16 位；浮点分支（高分辨率源走这条）不挂用户链、
   无从注入。故高分辨率源无论走哪条分支都得不到打包整型写出。

结论：要在只声明打包整型的设备上做直出，只能另起一个输出实现，不能在媒体3 的默认输出上嫁接。
现由 IntPcmAudioSink 承担：它自行按所设位深（24 位或 32 位）建轨，再交给媒体3 的 AudioTrackAudioOutput
托管（位置、欠载、变速、音量、音效都复用该实现，本层只做「接受解码数据—转成整型帧—写出」）。
两种位深共用一份实现，由 PerDeviceAudioSink 各持一个实例，按设备声明的条目切换。
与默认输出的差别：不裁剪编码器延迟与填充（曲目间隙略长），不支持静音跳过与隧道。
走不通的那版嫁接实现留档于 Temporary Test Resources/int24-回退存档，仅作记录。

不再事前建轨实测「能不能写出」（已核实，勿再引入）

打包整型是否只被少数机型受理、且没有能力查询接口——曾经据此写过一个「实际建一次探测轨道再释放」的
可用性实测（IntPcmOutputSupport），现已**整体删除**。两次实证都指向同一结论：

- 探测的结论取决于**探测时所处的现场**，与真正建轨时不一致，因此不可作为判据（同一档位在设备尚无输出
  时探测失败、起播有输出后探测通过）；
- 探测本身会把设备拖进坏状态：实测（KT02H20，Xiaomi 2107119DC / Android 14）在一次探测之后，**连 44100
  的浮点轨都建不起来**，播放随即以 ERROR_CODE_AUDIO_TRACK_INIT_FAILED 终止；探测还会按设备声明把 24 位、
  32 位逐档建一遍，而这些档位根本不在候选里（纯属白建轨）。

故现在的口径：

1. **「能不能写出」不再事前判定。** 候选只按「本应用写得出的编码」（writablePcmEncodings：16 位、浮点、
   打包整型）与设备**声明**的条目筛出，不做任何建轨试探——既不乱建档位，也不会拖坏设备。
2. **真正的判据只有两个，都在真实链路上：** 系统是否受理该混音器属性（setPreferredMixerAttributes 的
   返回值），以及音频轨是否真的建得起来。后者失败时由音频输出侧逐档降级兜底（见下条），不再把责任推给
   事前推断。
3. 已被证伪建不出音频轨的格式按会话、按设备记入不可用（UsbDirectOutput.unrealizableFormats），换设备即
   作废——避免同一失败被反复重试，也避免把某一台设备的坏档位记到新设备头上。

同理，被系统拒绝的混音器属性也不记成「已下发」：记下来会让同一条属性在之后的换曲里再不被重试。
判定「已受理」与抑制重复下发共用同一份状态（acceptedMixerAttributes），不接受「下发过」与「已受理」两本账。

动态混音端口查询会对「没有输出」的设备给空表（已核实，勿把空表当终局）

getSupportedMixerAttributes 不经 AudioService，而是 AudioManager 直查音频策略的原生接口；Java 层把任何
非 SUCCESS 一律折成空表，所以**空表有两种含义**：厂商没声明动态混音端口，或该设备此刻没有输出（平台按
输出端口应答）。实测同一台 KT02H20：应用未起播时查询得空表，起播后同一设备返回 7 条档位。

故「未声明动态混音端口」只能当作**当下这次问不到**，处理方式是把「声明」当成连接级的事实读一次：

- **问到之前一直重问**（UsbDirectOutput.onOutputEstablished，由音频输出的「音频轨已建立」回调驱动）。
  踩过的坑：开关在未起播时打开 → 空表 → 判定设备不支持 → 随后起播，输出已建成却没人再问，
  直出再也没回来（现象：受支持的源采样率也一直走混音，手动换曲同样无效）。
- **问到非空即认定本次连接的答案已定，此后不再问**（UsbDirectOutput.declaredFormatsFor）。厂商声明的档位
  是设备的固定属性，答案不会变；而查询的应答取决于「本应用此刻在该设备上有没有输出」，所以空表对判定
  毫无信息量、非空的答案则一直有效。只重问而不记住也不行：撤销直出会一并解除路由钉定，此后新起的输出
  不再落在该设备上，查询于是永远得空表（现象：末几首一路系统混音，且日志里连一条候选下发都没有）。

另一处必须成对：路由若在曲中才成立，写出变体不会自己跟上（变体只在音频输出重配点决策），故成色回调里
同时补一次重配（PerDeviceAudioSink.syncRouting，投回音频线程、变体未变则跳过）。少了它，状态会显示
「源格式直出」而音频轨仍以浮点写出——格式与偏好不符，AudioFlinger 静默混音，名不副实。

不再申请位完美：请求不到，请求到了更差（已核实于 frameworks/av 源码，勿再加回试探）

MIXER_BEHAVIOR_BIT_PERFECT 只是一条请求，而且这条请求**注定无效**：setPreferredMixerAttributes 把所请求的
行为并进用于匹配的输出 flags（AudioPolicyManager.cpp:5442 `audio_output_flags_from_mixer_behavior`），
IOProfile::getFlagsCompatibleScore（IOProfile.cpp:226）再要求「请求的每个 flag 都已在 profile 声明里」——
判据本体在 policy.h:312 `audio_output_flags_is_subset`：
`((superset ^ subset) & mustMatchFlags) == NONE && (superset & subset) == subset`，profile 是 superset、请求是 subset。
厂商没在动态端口上写 AUDIO_OUTPUT_FLAG_BIT_PERFECT，任何 profile 都过不了这一关，`profile == nullptr` 即
BAD_VALUE（AudioPolicyManager.cpp:5467）——**「厂商漏标而框架受理」这种可能不存在**，故 UsbDirectOutput 里
那次「先试后回落」的试探已整体删除（日志里那条每次都出现的「位完美请求被拒」也随之消失）。行为由 profile 的
AUDIO_OUTPUT_FLAG_BIT_PERFECT 反推（IOProfile::refreshMixerBehaviors），而国产厂商的 USB 声卡普遍不声明它
（实测已知两台：一台只声明 24 位整型，一台只声明 32 位整型，均只有默认行为）。

就算请求得到，这一档在本应用关心的事上**更差**，三处源码：
1. 位完美档会把**别的应用**的媒体轨吸到同一条输出上：AudioPolicyManager.cpp:1564 对别的 uid 保留偏好条目，
   当且仅当 `info->isBitPerfect() && info->getActiveClientCount() != 0`；随后 getOutputForDevices 按
   `info->getProfile()` 复用我们那条输出（AudioPolicyManager.cpp:1975 起），三等——采样率、声道、编码——
   一律不比。默认行为档下同一处 uid 闸门把条目置空，别人的轨进不来。
2. 别人一进来，旁路混音就没了：BitPerfectThread::getTrackToStreamBitPerfectly_l（Threads.cpp:12036）只在
   「除位完美轨外所有活动轨都被静音」时才直通，否则返回 nullptr、`mIsBitPerfect = false` 退回普通混音；
   而我们无权设置别人那条轨的音量。表现就是「卡顿一下之后两路一起响」，成色却仍显示位完美。
3. BitPerfectThread 本身就是 MixerThread（接受多轨），其 prepareTracks_l 专门处理「多条活动轨」的情形
   （注释：No need to copy bit-perfect data directly to sink buffer given there are multiple tracks active）——
   位完美不是独占，恰恰相反。

因此本应用只申请**默认行为**档（UsbDirectOutput.selectDirectMixer 只取 MIXER_BEHAVIOR_DEFAULT 条目）：
专用输出流照开、按源格式、不重采样，且保持单客户端。平台的混音行为枚举对每个动态输出端口恒有一条默认行为
条目，故只取默认条目不会挑不出档位。成色随之只有两档：源格式直出与系统混音。

余下的差别要说清楚：默认行为档的流仍经混音器（音量、挂在输出上的 effect 都作用），只是采样率与格式与源
一致——不保证样本值一字不变，只保证不被重采样。要样本值也不动，只有 raw USB（自己 claim 接口、内核
snd-usb-audio 解绑），代价是整条 USB Audio Class 输出自管，不在当前范围内。

（另有一条真正绕开混音的路：AAudio 独占/MMAP，数据直写驱动。它要求 HAL 声明 MMAP 支持，且需要另写一套
输出实现（时钟、位置、欠载都得自管），与 media3 的音频输出体系不兼容，同样不在当前范围内。）

变体切换的起停只由 play/pause 决定（已核实，勿在 reset 里清掉起停意图）

音频输出的起停状态由渲染器经 AudioSink.play/pause 下发，`reset` 只是资源操作。把 reset 当作「渲染器停了播」
会在播放中切轨时留下死结：reset 之后渲染器仍处于已启动状态（MediaCodecAudioRenderer.onReset 与
MediaCodecRenderer.reset 都不清除其 isStarted），此后不会再下发 play；于是新生效的变体——变体切换按登记的
播放意图接续（PerDeviceAudioSink.switchTo）——不会被启动，轨道位置随之冻结，媒体3 的停滞检测满 10 秒
即以 ERROR_CODE_TIMEOUT（"Player stuck playing with no progress for 10000 ms"）终止播放。
实测：一次直出格式改挂之后即撞上（现象：日志里「变体切换：FLOAT → INT32，保持暂停」，13 秒后播放失败）。

故 PerDeviceAudioSink.reset 只登记释放（outputReleaseRequested）而不动 playRequested，起停一律由
play/pause 决定。

受理混音器属性 ≠ 本应用真的用得上它（已核实，勿以受理为终局）

setPreferredMixerAttributes 的受理只说明设备侧存在匹配的动态输出 profile，**不说明本应用建得起与之
逐字段一致的音频轨、更不说明写得出去**。同一台机（KT02H20，Xiaomi 2107119DC / Android 14）两处都实测过：

- 按默认行为下发「48000Hz/2ch/24 位整型」，系统受理并进入「源格式直出」，随后
  IntPcmAudioSink 建轨抛 UnsupportedOperationException: Cannot create AudioTrack——AOSP 里该裸消息只出自
  Builder.build() 的「原生建轨失败、轨道停在 STATE_UNINITIALIZED」一处（AudioTrack.java:1563-1567），
  不是 Java 参数问题；该异常随 ERROR_CODE_AUDIO_TRACK_INIT_FAILED 终止了整曲播放。
- 另一档 24 位轨**建得起来、写不出去**：轨道建成后 write 返回 AudioTrack.ERROR_INVALID_OPERATION(-3)，
  播放随 ERROR_CODE_AUDIO_TRACK_WRITE_FAILED 终止。该错误码不在媒体3 的可恢复集（只有 ERROR_DEAD_OBJECT
  算可恢复），所以它会直接带走整曲播放，而不是交给渲染器重试。

三条结论：

1. **事前推断拦不住它，也不该去做。** 唯一的判据是真实建轨与真实写出；事前实测的结论取决于当时的现场，
   且探测本身会把设备拖坏（见上条）。
2. **唯一可靠的拦截点是 sink。** 生效变体建不起音频轨、或建起后写不出，都必须逐档降级：
   PerDeviceAudioSink 捕获 InitializationException 与 WriteException（后者只取不可恢复的一支），
   通知直出把该格式记为不可用并改挂下一档，本次缓冲续写；全部用尽才交**可恢复**错误（不以不可恢复错误
   终止播放）。直出是尽力而为，任何一环失败都不该把整曲播放带走。
3. **降级次序由设备声明的档位逐档退让得出，不用固定次序表。** 档位一律取自设备声明的动态混音端口条目
   （UsbDirectOutput.directMixerCandidates：与源同率的在先、同族整数倍的在后，不再按源位深与源采样率另拼
   候选去试探未声明的参数），故次序是「首选那一档 → 被证伪后次选那一档 → 无档位可用即系统混音」。
   固定次序表（曾为 FLOAT → INT16 → INT24 → INT32）做不到这一点：它不知道设备声明了哪些位深。
   位深优先序见 selectDirectMixer/encodingPreference：解码输出为浮点，不得落到 16 位档位——那正是
   「24 位源被写成 16 位」的来路。
   **续试在撤销之前做**：setPreferredMixerAttributes 是覆盖式的，改挂成功即无需撤销，设备也不会被解钉；
   撤销会把设备解钉、成色落回系统混音（免打扰白翻一次），并触发上一条那个「再也回不来」的死结。
   改挂不成才撤销——那条失败格式的偏好此刻仍挂着，不清掉 AudioFlinger 会继续静默混音。

   缓冲区间的处理两边不同，别混：建轨失败发生在对本缓冲的任何读写之前，可直接改交下一个变体；
   写出失败时缓冲可能已被消费（媒体3 的输出实现会就地消费输入缓冲），故统一退回本轮的缓冲起点再重试。
   失败的一方已随切换被释放，它接纳而未播出的数据不会再播出，整块重写才是连续的。
4. **该机的 24 位整型整档不可用，而设备声明的 32 位档位可用**：44100/24 被拒、48000/24 被受理但建轨抛
   异常、96000/24 被受理但写出失败。位深优先序使写出优先取容量更大的档位，故 24 位源在这台机上
   取到的正是 32 位（左移补零，逐位无损），不会再撞上 24 位轨；只有设备在该采样率下**只声明了 24 位**
   时才会用到它，届时它失败一次、记入不可用（UsbDirectOutput.unrealizableFormats，按格式记、换设备即
   清零），无档位可退才回系统混音。

解码输出恒取浮点（已核实，勿再按源位深收窄）

媒体3 只在**恰好**收到 `SINK_FORMAT_SUPPORTED_DIRECTLY` 时才向解码器索取浮点输出
（MediaCodecAudioRenderer 据此设 KEY_PCM_ENCODING），故能力基准报什么，解码输出就取什么。

PerDeviceAudioSink 的能力查询恒按浮点变体回答（PerDeviceAudioSink.getFormatSupport），不随源位深分化：
直出追求按源格式写出，解码统一落在浮点、由写出端按目标位深取整，精度只多不少；而按源位深把 16 位及以下
的源改答「需转换」，只换来一次 16 位解码与随之的又一次补位转换，收益为零，故**不再区分源位深**。

一位曾经的顾虑可以放下：面板的「解码输出」一栏展示的是解码头实际产出的编码，源位深另由容器头读出并经
audioSignalPathFormat 独立展示，两者不因解码恒取浮点而对不上。

起播前仍按容器头读一次位深与声道（MusicPlaybackState.recordSourceBitDepthBeforePlayback，切歌入口与
自动接续两处都调），但这只服务信息条在解码前的展示，与音频输出的申报无关。只读容器头、不读采样率与
比特率，后两项由轨道回调补齐。


同族倍率档：设备不声明源采样率时的直出出口（已核实，勿改成「让系统升采样」）

背景：设备（USB 解码器的动态混音端口）只声明 88.2kHz 而不声明 44.1kHz 时，按「与源同率」筛不出任何档位，
直出整体让位、播放交回系统混音——而系统混音器会把 44.1kHz 重采样到设备当时那档采样率（通常是 48kHz），
那是**跨时钟族**的任意比重采样。做法是给直出多一条候选：取设备声明里**同族整数倍**的那一档
（44.1→88.2、44.1→176.4、48→96…；判据见 sameFamilyMultiple：整除且倍率为 2 的幂，取最小倍率），
由本应用把数据按该倍率补齐后挂上去。同族即时钟同源，设备侧不必再做一次异步转换；整数倍即补出来的样本
不含任意比重采样带来的误差。

这不是「挑最接近条目」的退让——那是拿跨族档位凑合、数据要真的重采样。三条边界：

1. **倍率数据必须由本应用补齐**（SameFamilyUpsampler）。只把偏好设成 88.2 而仍写 44.1 的帧，写出的三项
   与混音器属性不匹配，轨挂不上专用输出流、AudioFlinger 静默混音，「绕开系统重采样」一句也不成立，
   而界面还会显示已直出。
2. **保真只有一条承诺：原样本逐位保留。** 半带结构把偶数相位做成「照抄半程之前那一个」，奇数相位才是插值
   出来的新样本，故这是构造上的保证而不是近似还原（实测影像抑制 -108dB、通带增益误差 4e-6，
   见 SameFamilyUpsampleTest）。代价说清楚：**不是位完美**——输出确实多了样本、DAC 也按倍率跑。
   解码输出的中间态用双精度：浮点与 32 位整型都能被它无损容纳，32 位源不会在这里丢低位。
3. **延迟与收尾成对，倍率变更只能整体重配。** 半带滤波有 48 个源样本（44.1kHz 下约 1.09ms）的固有延迟，
   故曲末必须冲一次尾段（PerDeviceAudioSink.playToEndOfStream → SameFamilyUpsampler.drain），不冲就是丢掉
   最后那一段原样本；曲首则是延迟线未灌满的渐入。降级重挑出的档位若换了倍率（或档位用尽而交回系统混音），
   必须先作废手里的余量再整体重配：余量是旧倍率下的数据，写进新档就是错速率的音频，比丢一段余量严重得多，
   而源缓冲未被消费、渲染器会原样再送一次，数据不丢。

展示口径：音频信息面板的「输出采样率」在直出成立时给**源采样率**（见 AudioInfoCollector.outputSampleRate
的注释）——内容频率与内容一个样本都没变，升采样只改样点密度；设备侧真实的流速率由诊断日志留痕
（输出成色那一条会打印已受理属性的采样率）。成色仍是「源格式直出」，心动模式的互斥判据不变。

落地位置：候选在 UsbDirectOutput.directMixerCandidates 与 selectSameFamilyUpsample；插值在
PerDeviceAudioSink（按倍率放大内层配置、写出前插值、余量握在本层、曲末冲段）。

输出采样率的两层口径（已核实，勿再混谈）

一处反复出现的分歧：说「本应用不协商采样率」还是「采样率跟着设备支持在走」，两者都对——答的是不同的问题。

1. 谁做的调整：本应用不重采样，也不为迁就设备挑采样率。直出档位只有两条来源，都出自设备声明的动态混音
   端口条目：与当前解码格式**同率**的那一条优先，缺席时退到**同族整数倍**那一条（倍率数据由本应用补齐，
   见上条与「同族倍率档」一节）。不做「挑最接近条目」的退让——那是拿跨族档位凑合、数据要真的重采样；
   也不按源位深与源采样率另拼一条去试探设备没声明的参数（那样换来的只是一次被拒，或一条受理了却写不出的
   轨道）。两条都挑不出即整体让位，输出路由与混音器属性一并撤销，播放交回系统混音。
2. 最终落在哪一档：设备侧那条流始终落在设备支持的那一档。同率档成立时输出即源采样率、数据一字不动；
   倍率档成立时设备侧落在同族倍率上（如 88.2kHz），而**内容速率不变**——原样本逐位保留、内容频率不变，
   故面板按内容口径显示源采样率。直出不成立时由系统混音器把源重采样到设备的采样率——
   AudioInfoCollector.outputSampleRate 此时读的是设备的 PROPERTY_OUTPUT_SAMPLE_RATE，
   与源不等即在音频信息面板标为已重采样。

故「动态适应设备」作为结果描述成立，「本应用不协商采样率」作为机制描述也成立；把二者说成互相否定的，都是只读了一层。
副标题取的是结果口径。

系统导航栏（虚拟按键）适配（已核实，勿只留一处）

「虚拟按键压在播放控制按钮上」不是布局写错，而是两件事叠加：三键导航栏默认带一层系统铺的不透明底色，
且 edge-to-edge 下底部偏移被取消、内容默认延伸到导航栏后面。下面几点共同构成适配，删掉任一点都会退回原状：

1. `MainActivity` 在 `enableEdgeToEdge` 之后必须显式 `window.isNavigationBarContrastEnforced = false`。
   只靠 `enableEdgeToEdge` 拿不到全透明导航栏：其默认 `navigationBarStyle` 为 `auto`，而 `auto`
   会打开强制对比度（API 29+ 由 androidx 设 true，API 35+ 平台默认即 true），三键导航栏被铺上不透明底色。
   `auto` 与 `light/dark` 的差别就在这个属性，与传入的 scrim 颜色无关。
2. 首页竖屏与横屏一并全沉浸：`isHomePortraitImmersive` 同样走 `HIDE_ALL`，首页（含在线搜索页、歌单页）
   隐藏状态栏与导航栏两条。沉浸只下发隐藏、不裁剪布局——上滑临时唤出的系统栏以覆盖方式呈现，
   不改变 insets，故界面侧不必为它做避让。
3. 仍显示系统栏的页面（设置/排版/频谱/存储管理/元数据）各自避让导航栏高度，无一处统一兜底：
   滚动页把避让加在滚动容器上（`navigationBarsPadding`，见 `CacheGroups` 原注释）；
   带键盘的页一律取 `WindowInsets.ime.union(navigationBars)`（元数据编辑页）——键盘展开时其高度
   已含导航栏区域，直接叠加会让出两段高度。
4. 首页的避让分两类。搜索页与歌单页列表在沉浸态下取值恒为 0，保留并非冗余：导航栏被外部原因
   显示出来时（独立窗口、切页过渡、ROM 不认隐藏请求）仍能保证底部控件不被压住。
   竖屏播放页的 `bottomClearance` 则取固定留白 `BottomBarClearance`（24dp）与导航栏高度的较大值，
   沉浸态下不为 0 —— 底部留白由该固定值决定，而不是由「屏幕高宽差减去内容高度」的余量决定；
   后者随屏幕尺寸与高宽比漂移，同一套布局在不同机型上会忽高忽低。竖屏播放页的高度分配也不再用
   手工估算的内容高度：封面、歌词组、信息/控制组三组之间由 `Arrangement.SpaceBetween` 分配，
   封面为 `weight(1f, fill = false) + heightIn(max = 全宽正方形)`（保留正方形、窗口过矮时收缩），
   富余空间只落入封面↔歌词、歌词↔歌曲信息两处，把歌词组夹在中间均分，内容高度交由系统实测。
   两个底部弹层（播放列表、音频信息）是例外，不避让导航栏：面板底色
   铺到屏幕底缘，在面板根节点预留这段高度只会在底部留下一条与底色同色、不随内容滚动的色带，
   与「元数据编辑页去掉固定底部内边距」是同类问题；面板自身的底部内边距同理取消，只留左右与顶部。
   播放列表弹层仍避让键盘（`imePadding`）——键盘自身已覆盖导航栏区域，无需再叠加导航栏高度。
5. 图标颜色按「图标底下压着什么」定色：首页是深色封面衍生背景，故固定白色（`HomeScreen` 的 `SideEffect`），
   弹层展开时改回按主题取色；其余页面由 `StatusBarStyleEffect` 统一声明。


播放模式新增枚举值只能追加在末尾（已核实，勿再调整顺序）

`PlayMode` 的序号以 ordinal 落盘（`music_saved_mode` 与播放状态快照的 `mode` 字段各一份），
读取时按 `PlayMode.entries.getOrElse(savedMode)` 还原。**在中间插入新值会让已装机用户保存的序号
整体错位** —— 保存的 1 原意是 RepeatAll，插入后会被解析成它前面那个值。新增模式一律追加在末尾，
心动模式（`Highlight`）即按此追加。

心动模式的片段播放不得计入完整播放（已核实，勿放开）

心动模式播的是 30–45 秒的副歌片段，若照常计入 `recordPlayed`，会同时坏掉两处：

1. 常听（`recentPlayedIds`，3 天内播够 2 次）会把每首都收进来，常听歌单失去意义；
2. `PlaylistSort` 等按播放记录排序的路径随之失真。

故 `recordPlayed` 的两个调用点（`onMediaItemTransition` 与 `STATE_ENDED`）都以
`playMode != PlayMode.Highlight` 为前提。裁剪后片段的结束由播放器按「自然播完」上报，
不加这道闸就会静默计入。


心动模式的片段一律取自持久化表（已核实，勿改回播放时解析）

片段的「算」与「用」必须是分开的两段：

- **算**：`HighlightScanner` 在后台成批扫描全库，结果连同「歌词 + 时长 + 算法版本指纹」由
  `HighlightStore` 落盘。指纹未变不重算；歌词补齐、时长补全或算法升级后指纹改变，自动重扫。
  启动恢复完成、曲库变化、启用心动模式三处触发。歌词此刻取不到的曲目记为 `Unresolved`
  而**不是** `NoChorus` —— 前者只是数据未就绪，据此跳过会让歌词尚未补齐的曲库被整库跳过；
  后者才是真的没有高潮段，只有它才跳过该曲。
- **用**：播放路径只做一次内存查表（`HighlightStore.segmentOf`）。切歌、切模式都不读盘、不定位。

历史上曾在播放路径上按需解析（切歌时读歌词并定位，再逐项替换队列里的 MediaItem 补片段）。
那条路有三个必然的毛病，故不要再改回去：每次切歌都要读盘与计算；片段何时生效取决于歌词何时就绪，
行为不确定（表现为「开了模式却没有片段」）；切换模式要逐项替换队列，队列长时明显卡顿。
还有一个隐蔽的坑：当时的队列一致性判定只比 mediaId 与 URI，看不见裁剪差异，新构建的「带片段的项」
会被判成「队列没变」而跳过装载。现在整队列按片段表一次性重建，`sameQueue` 里保留裁剪区间比较作兜底。

模式切换对当前曲目立即生效（进入自片段起点起播、退出还原到整曲的绝对位置），不是「从下一曲才开始」。
因此落盘的播放位置必须是**整曲的绝对位置**（见 `persistablePositionMs`）：控制器回报的是片段内进度，
直接落盘会让恢复时对不上；恢复由 `mapSavedResumePosition` 换算回片段坐标系，两个方向对称。

片段的收尾一律落在**歌词行的边界**上（见 `HighlightLocator`）：先纳入整个副歌块，
再逐行补到时长下限，上限用「再补一行就会超出」判定，于是最后一行总能唱完，
而不是被 45 秒硬切在半句上。块自身就长过上限时**必须向回收缩**到 45 秒以内，不得把整块原样返回。
收尾另取「下一行起点」与「末字演唱终点」的较大者：逐字歌词的末字可能唱到下一行起点之后，
只认下一行起点会把这一行截断，这正是「末句没唱完就被切走」的成因。



心动模式只做纯歌词分析，不解码音频（已核实，勿改回音频精修）

副歌定位（`HighlightLocator`）只用歌词文本与时间戳，分四步：

- **重复结构**定候选：副歌在歌词上表现为同一批行反复出现，这是 RefraiD、pychorus 一类副歌检测的
  共同前提（副歌是整曲重复次数最多的段落）。只出现一次的行块不成候选；制作信息行（作词/作曲……）
  复用 `LyricFeatures.cleanLyrics` 的同一套前缀判据剔除，避免整段重复的信息行被判成副歌。
- **位置、时长、密度、停顿、结尾权重**给候选打分：首现越晚、时长越贴合 30–45 秒、片段内行越密
  （每秒行数越多）、行间最大间隔越短、越靠近曲末的块越像副歌。
- **取最后一遍完整副歌**：每个候选只收其最后一次能成段的出现 —— 末遍副歌通常是全曲落点，
  且收尾落在歌词行边界上；末遍短到收不出片段时退回上一遍。
- **不取歌词行数少的片段**：候选按片段内行数降序排列，行数相同再比得分，于是「高潮必是 30–45 秒内
  歌词行数最多的一段」直接落在排序首位，稀疏段落自然落选。

**为什么不做音频**：逐曲解码全曲能量（`MediaCodec` 解 PCM、逐帧求响度与高频占比）在整库扫描上
代价偏大，对「有清晰重复副歌」的绝大多数流行歌并不提供额外信息；而把精修推迟到进入模式时才做，
又让片段何时生效依赖扫描时机，行为不确定。改为纯歌词后，扫描只读歌词与时间戳，代价低且与当前
模式无关。为此 `EnergyEnvelope` / `HighlightSelector`（音频兜底与响度谷吸附）连同条目上的
`refined` 标记一并移除；算法版本升至 `v4`，旧结果按指纹整体作废重算。

「有歌词却乱播或漏播」的两个来源据此封死：乱播（把重复的主歌当副歌）靠「行数最多 + 五项打分」纠正；
漏播（歌词无时间轴）判为 `Unresolved` 退回整曲播放，**只有「有可用歌词时间轴 + 确实收不出片段」
才判 `NoChorus` 跳过该曲**，歌词尚未补齐的曲库不会被整库跳过。


心动模式下两套时间坐标不得混用（已核实，勿凭直觉取用）

播放器回报的位置以**片段起点为原点**，而歌词行的时间戳是曲目内的**绝对时间**。
两者只允许在状态层换算，各消费点按用途取值：

- **歌词一律取绝对时间**：`MusicPlaybackState.lyricPositionMs`（= `livePositionMs` + `highlightPositionOffsetMs`）。
  竖屏歌词的跟随锚点、悬浮窗迷你播放器、长按歌词定格编辑目标行，三处都取它。
  它们曾直接读 `livePositionMs`，于是心动模式下整段歌词落后一个片段起点 —— 这就是
  「歌词没跟随片段」的成因。
- **进度条取片段相对时间**：`currentPosition` / `duration` 原样使用，它要的正是「这一段播了多少」。
  显示成 0:12 / 0:40 而非 1:22 / 4:05 是有意的。
- **以歌词行为目标的跳转必须换算**：歌词行给的是绝对时间，`seekTo` 的目标必须是片段坐标系，
  经 `toPlayerPosition` 换算；不换算会落到片段之外被播放器钳到边界。
- **落盘与恢复的坐标**：落盘存整曲绝对位置（`persistablePositionMs`），
  恢复经 `mapSavedResumePosition` 换回片段坐标系。

新增任何读播放位置的界面时，先问一句：我要的是「这一段里的进度」还是「整曲里的时间」。


心动模式与音频直出互斥（判据是取向，不是音量；勿放开）

USB 直出（`AudioOutputMode.FORMAT_LOCKED`）成立时必须退出心动模式，且直出期间不接受再进入：直出为整曲
保真聆听服务，与「把每首裁成 30–45 秒片段」取向相斥。判定以**实际输出成色**为准，不看设置开关 —— 开关
打开而设备不支撑时播放仍走系统混音，此时心动模式照常可用。

（历史：本条原先还列了一条技术理由——「位完美一档绕过系统混音、音量与音效都不生效，片段首尾靠
`Player.volume` 的淡入淡出无从实施」。位完美档已整体移除，本应用用的源格式直出档**按常规链路处理音轨
音量**，那份淡入淡出在其上是生效的；故互斥若日后再议，只剩取向这一条判据，不再有技术障碍。）

片段首尾的淡入淡出靠降低播放器音量实现，不进音频数据

片段由裁剪（`ClippingConfiguration`）切开，首尾都是硬切；`MusicPlaybackState.syncHighlightFadeVolume`
在片段开头把 `Player.volume` 由 0 升到 1、在结尾前由 1 降到 0，掩掉突兀的进出。位置与时长都取控制器
对当前项的回报（裁剪后即以片段为原点）。要点：

- **只对确有片段的曲目生效**：心动模式下没有片段的曲目照常整曲播放，不该被从头淡入到尾。
- **片段播放期间进度轮询加密到 40ms**：200ms 的台阶会让斜坡听成几次跳变；非片段播放仍为 200ms。
- **退出心动模式须即刻把音量复位到 1**：否则淡出末尾的低音量会被整曲播放沿用。

设备没有该编码的解码器时播放无声且不报错（已核实，勿只按解码器初始化回调判断当前解码器）

媒体3 的音频渲染器在设备没有该 mime 的解码器时，把整条音频轨判为不支持
（MediaCodecAudioRenderer.supportsFormat：解码器列表为空即 FORMAT_UNSUPPORTED_SUBTYPE），
ExoPlayer 随之**不选中**该轨——表现为静音走完、播放器不报错，且不会有解码器初始化回调
（`onAudioDecoderInitialized` 不触发）。在《02. 願我可以學會放低你 [ALAC] [16 bit - 44.1 kHz].m4a》
（真身是 MP4 内的 alac 采样描述，16bit/2ch/44100，容器头解析无误）上实测到两个后果：

1. **残留解码器名会顶着当前曲目继续展示**：`MusicPlaybackState.audioDecoderName` 只在解码器初始化回调里
   写入、原先不随切歌清空——上一首 flac 曲目的 `*.flac.decoder` 会一直显示在 ALAC 曲目的音频信息面板上，
   正是「M4A 里的 ALAC 被说成用了 flac 解码器」的来路。现由 `MusicPlaybackService` 的轨道回调按
   「本轨未被选中（无解码器）」与「音频轨换了编码」两种情形清掉，面板改由 `AudioInfoCollector` 给出
   「不可用（本设备不支持 ALAC）」。判据只能是轨道选中状态：解码器名与 mime 都拿不到「本机能解什么」。
2. **无声与「本机解不了」无从区分**，故该情形记一条诊断日志（含 mime 与曲目）并给出提示文案
   （`music_panel_decode_unsupported`）。

ALAC（`audio/alac`）在 AOSP 内**没有**解码器（Codec2 组件与 SoftOMX 的组件表里只有 flac/aac/mp3/opus/…，
Android 官方「支持的媒体格式」表也没有 ALAC 行），能否播放取决于厂商是否提供；本机没有即无法播放，
不能靠容器头解析或换 mux 名字绕过。

自研 ALAC 解码器（补齐 AOSP 缺失的 audio/alac）

上一条记的是「本机没有解码器就只能无声」。现已以自研解码器补齐该格式：接入点取媒体3 官方给出的扩展机制
`DecoderAudioRenderer`（flac/opus 扩展渲染器走的是同一条路），在 `MusicPlaybackService` 的渲染器工厂里
**追加**在默认音频渲染器之后——厂商若自带可用的 `audio/alac` 解码器，媒体3 仍会优先选中它，自研实现只在
系统解不了时接手。解码核心（`data/music/playback/alac/`）不依赖 Android，可脱离设备单测。

三处口径必须与既有的 MediaCodec 路径一致，否则同一首歌在两条路径下会得出两种结论：

1. **解码输出取浮点**，判据与 `MediaCodecAudioRenderer` 相同（接收器能**直接**受理浮点才索取浮点输出）。
   USB 直出按解码输出格式挑混音器属性、音频信息面板按它显示「解码输出」，两处都读这一个值。
2. **渲染器直接构造**（`out.add(AlacAudioRenderer(...))`），不经反射，故不需要额外的 keep 规则。
3. **解码器名**上报的是自有实现（`yichao.alac.decoder`），面板上可直接看出这条轨由谁解。

实现上有两个坑，改这段代码前先看一眼：

- **帧尾的越界读取必须按 0 补齐，不能读相邻帧的字节**：参考实现的比特缓冲一次取 4 字节，帧尾字段的读取
  本就跨过样本末尾。零补齐与「读到下一个样本」都能解出看似合法的结果，但后者会让同一条流随前一条数据的
  不同而解出不同结果（解码输入缓冲被复用时即不成立）。
- **残差余数段在余数小于 2 时少占一位**：这是 ALAC 的编码约定，漏掉这一位会让位流位置逐样本漂移——
  开头几百个样本仍解对，之后整段失真且不报错。

校验方式：与 FFmpeg（不依赖本实现）对同一条曲目的解码结果逐字节比对，全曲 2827 帧 / 46,306,176 字节
零差异；仓库内保留前 14 帧与末帧（唯一自带样本数的分片帧）的逐帧摘要作回归。

容器扩展名不能当格式名（`.m4a` 里的 ALAC 曾被说成有损）

`.m4a` 里的 ALAC 曾显示成 `M4A`，并因此被判成有损、被提示做无损升级——格式名有两处产出，原先都是
「扩展名优先」，而 `.m4a` 只是容器扩展名：里面可能是 AAC，也可能是 ALAC。现由一条共享规则
（`FormatDisplayName.kt`）统一：扩展名能定案就用扩展名，扩展名属于容器时改看 mime，容器头有正面
认定结论时优先用它（`ContainerFormat.codecName`）。

同一族的容器扩展名一并过了一遍，判据是「该容器能否装下无损内容」：

| 扩展名 | 处理 | 理由 |
| --- | --- | --- |
| .m4a / .mp4 / .m4b | 容器头正面认定 ALAC | ISO-BMFF 家族，有声书的 .m4b 同样可能装 ALAC |
| .caf | 不纳入（整体不支持） | media3 无 CAF 提取器，文件连装载都过不了，见下 |
| .m4p / .m4r | 交给 mime | 受保护 AAC 与铃声，内容恒为有损，不值得为其多开一次文件 |
| .ogg/.oga/.mka/.webm/.3gp | 交给 mime | 内容是 Vorbis/Opus/AAC 等有损编码 |

改这段代码前要看一眼的几点：

- **CAF 不做任何处理**：media3 的提取器表里没有 CAF（AC3/AC4/ADTS/AMR/FLAC/FLV/Matroska/MP3/MP4/
  Ogg/PS/TS/WAV/JPEG/AVI/PNG/WebP/BMP/HEIF/AVIF），`caff` 魔数在任何地方都不认识，`.caf` 文件连装载
  都过不了、必然报错。因此不为它写容器解析，也不在格式名规则里给它留位——留着只会让人以为支持它。
- **容器头认定与「值不值得读盘」的门限必须对得上**（见 `isContainerHeaderFormat`）：格式名说不出码流
  的那一族若在门限上被挡下，容器头这条路径就形同虚设。
- 曲库按格式分类（`trackFormatCategory`）仍按扩展名走，有意为之：`.m4a` 作为曲库归类维度是合理的，
  与「这条轨是什么码流」是两件事。

已知未覆盖的两处（都是保守方向的错，不会误报升级）：

- **Ogg 里的 FLAC**：起播后由提取器的 mime（audio/flac）能定案，未播放时的预读只认得出容器，那一格会显示成 OGG。
- **`.wav` 里装 MP3**：位深照 `fmt` 块可信，但码流按扩展名仍算无损。

元数据编辑对「奇葩容器」的适配（大封面 M4A、分片 MP4、Ogg Vorbis）

**一、M4A 的标签读不到，编辑页打开是空表单。** 实测两首歌（`Temporary Test Resources` 里 3000×3000
封面的 ALAC 与 Bilibili 打包的分片 AAC）都是这个形态：`ilst` 下 `covr` 封面排在文本原子**之前**，
封面 1.1MB / 1.8MB，全部文本原子落在 1.2MB / 1.8MB 之后。读取端按「固定 512KB 头窗内解析」，
遍历遇到超出窗口的盒子即判结构不完整并返回，于是整份标签一个字段都读不到——用户把空表单存回去
就等于抹掉文件里的既有标签（内嵌歌词同样读不到）。

修法：`Mp4TagReader` 按盒子头逐层定点下钻（moov → udta → meta → ilst），只读盒子头与命中原子的载荷，
封面原子只读头不读体；读取走滑动窗口（连续小原子共用一次读取，载荷越窗即跳到该原子末尾另起一段），
读取量与封面尺寸无关——实测两首歌分别定点读 96KB / 64KB 即取回全部字段与歌词。

- 写入端本来就能处理这些文件（音频区逐字节不变），出错的是**读取端**：改这类问题要把两条路径的容器口径一起看。
- 歌词原子（`©lyr`）与文本标签同在 `ilst` 下，`MusicEmbeddedLyricReader.readMp4Lyrics` 走同一套定位。

**二、分片 MP4 写入会把尾部整段读进内存。** 搬运判据此前是「**单个**顶层盒子超过 32MB 才拒绝」，
而 DASH 式分片的尾部是成百上千组成对的 moof+mdat，每块都不大、合计可达数百 MB；原实现把它们全部
读进内存（8MB 样本即搬 5.9MB，大文件会被系统回收进程且不产生崩溃日志）。改为按「被 moov 分开的
两侧中**字节更多的一侧**」整段流式搬运，另一侧（只含 ftyp/free 这类小盒子）按字面字节重建。

**三、Ogg Vorbis 的标签此前完全写不进。** 写入分派只认 `OpusHead`，Vorbis 文件整体落到「识别不出容器」
而被拒绝（读取端一直支持它，于是表现为「能读不能写」——在线下载的 .ogg 高品多为 Vorbis）。现在按包头
分辨注释包：Opus 为 `OpusTags`，Vorbis 为 `vorbis`，两者载荷结构一致；差别只在 Vorbis 末尾要多
一个**框架位字节**（0x01），缺它解码器判流损坏。

**CAF 与 AIFF 相关支持已整体移除。** 两者一度都有各自的容器头解析、无损判定、标签读写与读取门限，
但核对 media3 源码后确认：提取器表里既没有 CAF 也没有 AIFF（`extractor` 下只有 wav/flac/mp3/mp4/ogg/
mkv/ts/flv/amr 与各类图片），`caff` 与 `FORM`/`AIFF` 魔数在 media3 里一次都没出现；没有提取器就连媒体项
都装载不了、必然报错，于是两者的容器解析、格式名与无损判定、标签读写、读取门限与测试一并删掉
（CAF 见上表 `.caf` 一行）。

校验方式：两个真实文件走应用自身的读取入口（编辑器回填）与写入路径，产出交 FFmpeg 独立核对——
音频逐包与解码 PCM 摘要一致、封面可解码、标签回读正确；Ogg Vorbis 的产出另核对注释包字段与框架位。
