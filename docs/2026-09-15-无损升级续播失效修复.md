# 2026-09-15 无损升级后不自动续播修复

## 现象

1. 升级音质后不自动续播，必须手动点播放。
2. 升级后**未切歌**直接退出并重启，点击播放无法续播；切歌一次后恢复正常。

## 根因

### 原因一：换源走了 `playTrackAt`，重建了整个时间线

"简化直接续播"把换源实现为 `playTrackFromProgress` → `playTrackAt`。
`playTrackAt` 因 URI 变化判定 `sameQueue = false`，执行
`controller.setMediaItems(...)` + `controller.prepare()` —— 这是**重建整条播放队列**，
播放器进入重新准备流程，起播被打断，用户需手动点播放。

历史可用的 `refreshCurrentPlaybackSource`（见 `a26b588`）用的是
`controller.replaceMediaItem(index, newItem)`：就地替换当前项。媒体 ID 未变，
播放器不离开当前项，不进入准备流程，播放自然接续。这正是被"简化"掉的关键点。

### 原因二：升级后未立即持久化新 URI 与续播位置

进度持久化走 3 秒节流（`STATE_PERSIST_INTERVAL_MS`）。升级完成后若用户在窗口内退出，
落盘的仍是**旧 URI**，而旧文件已被 `deleteOldAudioFile` 删除：

- 冷启动 `restoreCurrentTrack` 按 `audioUri` 匹配不到（旧 URI 已不在列表）→ 兜底 index 0，进度作废；
- 或 `removeUnavailableExternalTracks` 判定旧 URI 不可用 → `clearSavedState` 清掉 URI 与进度。

切歌后之所以恢复：`onMediaItemTransition` 会立即 `persistState()`，写入的是新曲目的可用 URI。

## 变更

- `MusicPlayerHelper`：`playTrackFromProgress` → **`swapCurrentSourceToUri`**。
  用 `replaceMediaItem` 就地换源，按原进度 `seekTo`；`playbackState == STATE_IDLE` 时补 `prepare`；
  保持原有播放意图（播放中续播、暂停中保持暂停）。同时设置续播锚点，
  因 `replaceMediaItem` 会派发列表变更过渡回调。
- `MusicPlaybackState`：新增 `resumeAnchorTrackId`，锚点记录归属曲目；
  过渡回调仅在 `resumeAnchorTrackId == id` 时消费锚点。`softRelease` / `release` 一并复位。
  `playTrackAt` 设锚点时同步写入该字段。
- `MusicDownloader.upgradeTrackToLossless`：换源后、删除旧文件前立即 `persistState()`。
- 音频信息条无需额外处理：`MusicPlaybackService.onTracksChanged` 按 `currentTrack.path`
  重算格式，换源即刷新。

## 坑

- **换源不要重建队列**：`setMediaItems + prepare` 会重置播放器状态导致起播中断；
  同曲目换源必须用 `replaceMediaItem` 就地替换。
- **锚点必须带归属**：异步过渡回调顺序不保证，只按位置判断有效性会被同曲目换源场景击穿。
- **换源类操作要立即持久化**：源已变更但快照未更新的窗口内退出，会把已失效的旧 URI 落盘，
  造成重启后曲目不可用与进度丢失。
