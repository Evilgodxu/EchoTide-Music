# 2026-09-15 无损升级后按原进度直接续播（简化接替逻辑）

## 原实现的复杂度

无损升级完成后为了"不中断"，曾做成**自然接替**：

1. `refreshCurrentPlaybackSource`：`replaceMediaItem` 把当前播放项换成新无损文件，
   替换前记录 `wasPlaying` / `currentPosition`，替换后 `seekTo` + `play/pause` 恢复；
2. `scheduleOldFileDeletion`：以 `mediaController.currentMediaItem` 的**真实 URI** 判定旧文件是否
   仍被占用，占用则登记 `queueOldFileDelete`，待 `onMediaItemTransition` 时 `flushPendingFileDeletes` 再删；
3. 相关状态（`pendingFileDeletes`）常驻 `MusicPlaybackState`，删除时机跨越下载与播放两个模块。

问题：逻辑分散在三个文件、删除时机依赖对播放器内部 URI 的推断，难验证也难解释。

## 设计预期（简化后）

> 原低音质曲目点击音频信息条 → 显示升级 → 用户确认 → 下载无损音质 → 替换旧音乐文件 →
> **直接按当前进度开始播放**

升级完毕即播放，不再判断原播放/暂停状态、不再延迟删除旧文件。

## 变更

- `MusicPlayerHelper`：`refreshCurrentPlaybackSource` → **`playTrackFromProgress(context, state, index, positionMs)`**。
  设好续播锚点（`pendingSavedUri` / `pendingResumePosition`）后直接
  `playTrackAt(index, autoPlay = true, clearQueue = false)`，重建时间线并从记录位置起播。
  播放列表已指向新文件，无需单独 `replaceMediaItem`，也无需记录/恢复播放状态。
- `MusicDownloader.upgradeTrackToLossless` 线性化：
  下载 → 承接封面/背景 → 记录当前进度 → 索引转向新文件（含 `path`）→ 写元数据 → **按进度起播** → 删旧文件 → 媒体扫描。
- `MusicPlaybackState`：删除 `PendingFileDelete` / `pendingFileDeletes` / `queueOldFileDelete` /
  `flushPendingFileDeletes`，以及 `onMediaItemTransition` 中的 flush 调用。旧文件删除回到调用方，
  起播后直接删。

## 保留

- `SystemThumbnailCache.remap` 与 `remapGradientUri`：升级只换音频文件，封面与背景取色必须承接，
  否则新文件系统略缩图就绪前会闪占位符、回落默认色（见 `2026-09-15-无损升级保留封面背景.md`）。
- `embedUpgradeMetadata` 仍在**起播前**执行。

## 坑

- **元数据写入必须在起播前**：新文件一旦接入播放再被重写（内嵌封面/标题），会出现无声与进度反复回退。
  故流程顺序固定为"写元数据 → 起播"，不能为了先出声而调换。
- **升级期间切歌**：只用 `upgradedIndex >= 0 && currentTrack?.id == track.id` 判定是否就地续播；
  用户已切到别的歌时只完成文件替换，不打断当前播放。
- 音频信息条读的是**实际播放源**（`onTracksChanged` 依 `currentTrack.path` + 解码格式计算），
  必须真正切源才会刷新为新格式；只改 `currentTrack.audioUri` 不会刷新信息条。
- 旧文件在起播后删除：播放源已切到新文件，旧文件即使仍被持有句柄也不影响新文件播放
  （Android/Linux 下 unlink 不破坏已打开的 fd）。
