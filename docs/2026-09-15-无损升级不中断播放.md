# 2026-09-15 无损升级自然接替（不中断、不同步、信息条即时更新）

## 根因（两次迭代）
1. 最初升级调用 `refreshCurrentPlaybackSource` 对当前播放项 `replaceMediaItem` 切到新无损文件，
   源切换存在短暂重置，被感知为中断。
2. 改成“旧文件继续播到自然结束、下次播放再用新文件”后不中断了，但音频信息条读取的是**实际播放源**
   （`onTracksChanged` 依 `currentTrack.path` + 解码格式计算），旧文件未停则信息条一直显示旧格式，
   用户误以为未升级而重复点击，甚至重复下载。

## 结论：自然接替 = 切换播放源到新文件，旧文件延迟删除
- `refreshCurrentPlaybackSource`（恢复）：无损升级完成即替换当前播放项指向新无损文件，记录播放状态与
  进度并恢复（播放中续播、暂停保持暂停）。播放器随即以新文件播出，`onTracksChanged` 触发，
  音频信息条与系统媒体面板同步更新为新格式，杜绝重复升级。
- `scheduleOldFileDeletion`（保留）：旧文件是否仍被播放器占用以 `controller.currentMediaItem` 的真实
  URI 判定；占用则登记延迟删除（播放离开后再由 `onMediaItemTransition` 清理），否则立即删。
  由于 `replaceMediaItem` 经 MediaController 异步生效，切换后片刻 `currentMediaItem` 可能仍是旧文件，
  故此处多半走延迟删除，天然规避“边播放边删”的中断。
- `MusicPlaybackState`：保留 `queueOldFileDelete` / `flushPendingFileDeletes`（挂在
  `onMediaItemTransition`）/ `deleteAudioSourceByRef`（`deleteAudioSource` 委托它）。

## 坑
- 判定旧文件是否正被播放不能看 `currentTrack.audioUri`（升级后已指向新文件），须取
  `mediaController.currentMediaItem.localConfiguration.uri`。
- 音频信息条不以 `currentTrack` 直接决定，而是随实际播放源切换后在 `onTracksChanged` 重算，
  所以必须真正切源信息条才会更新；仅改 `currentTrack.audioUri` 不会刷新信息条。
