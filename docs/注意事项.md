打包整型输出无法嫁接在 media3 的默认音频输出上（已核实，勿再尝试）

背景：部分机型的 USB 动态混音端口只声明打包整型：较早的一批只声明 24 位（PCM_24BIT_PACKED），
部分 USB 耳放/解码器（如 KT02H20）只声明 32 位整型（PCM_32BIT），两者直出要成立都得写出该编码；
而 media3 的 DefaultAudioSink 只产出浮点与 16 位整型。曾按「改写 AudioOutputProvider 给出的输出编码、
在 AudioOutput 层转换字节」实现，结果是启用直出即播放崩溃（BufferUnderflowException → 播放错误），
且两次崩溃点完全相同。原因如下，三条互相封死了轻量方案：

1. DefaultAudioSink 会把管线缓冲与所声明的输出编码一并交给音量渐入：
   setOutputBuffer → maybeRampUpVolume → PcmAudioUtil.rampUpVolume(buffer, outputConfig.encoding, …)。
   渐入只在开头约 200ms 内生效（writtenFrames < rampFrameCount），此时按 24 位步长读浮点缓冲即越界。
   声明编码与实际数据不符，是崩溃的直接原因。
2. 让声明编码与数据一致（都保持浮点）也不行：AudioTrackAudioOutput.pcmFrameSize 取自 config.encoding，
   会按浮点算出 8 字节/帧，而 24 位整型轨道实际每帧 6 字节，位置与欠载记账会差三分之一。
3. 唯一自洽的做法是让管线真的产出目标位深，但用户处理器链只挂在整型分支：
   整型分支会先经 ToInt16PcmAudioProcessor 把高分辨率源截成 16 位；浮点分支（高分辨率源走这条）不挂用户链、
   无从注入。故高分辨率源无论走哪条分支都得不到打包整型写出。

结论：要在只声明打包整型的设备上做直出，只能另起一个输出实现，不能在媒体3 的默认输出上嫁接。
现由 IntPcmAudioSink 承担：它自行按所设位深（24 位或 32 位）建轨，再交给媒体3 的 AudioTrackAudioOutput
托管（位置、欠载、变速、音量、音效都复用该实现，本层只做「接受解码数据—转成整型帧—写出」）。
两种位深共用一份实现，由 PerDeviceAudioSink 各持一个实例，按设备声明的条目切换。
与默认输出的差别：不裁剪编码器延迟与填充（曲目间隙略长），不支持静音跳过与隧道。
走不通的那版嫁接实现留档于 Temporary Test Resources/int24-回退存档，仅作记录。

不再事前建轨实测「能不能写出」（已核实，勿再引入）

打包整型是否只被少数机型受理、且没有能力查询接口——曾经据此写过一个「实际建一次探测轨道再释放」的
可用性实测（IntPcmOutputSupport），现已**整体删除**。两次实证都指向同一结论：

- 探测的结论取决于**探测时所处的现场**，与真正建轨时不一致，因此不可作为判据（同一档位在设备尚无输出
  时探测失败、起播有输出后探测通过）；
- 探测本身会把设备拖进坏状态：实测（KT02H20，Xiaomi 2107119DC / Android 14）在一次探测之后，**连 44100
  的浮点轨都建不起来**，播放随即以 ERROR_CODE_AUDIO_TRACK_INIT_FAILED 终止；探测还会按设备声明把 24 位、
  32 位逐档建一遍，而这些档位根本不在候选里（纯属白建轨）。

故现在的口径：

1. **「能不能写出」不再事前判定。** 候选只按「本应用写得出的编码」（writablePcmEncodings：16 位、浮点、
   打包整型）与设备**声明**的条目筛出，不做任何建轨试探——既不乱建档位，也不会拖坏设备。
2. **真正的判据只有两个，都在真实链路上：** 系统是否受理该混音器属性（setPreferredMixerAttributes 的
   返回值），以及音频轨是否真的建得起来。后者失败时由音频输出侧逐档降级兜底（见下条），不再把责任推给
   事前推断。
3. 已被证伪建不出音频轨的格式按会话、按设备记入不可用（UsbDirectOutput.unrealizableFormats），换设备即
   作废——避免同一失败被反复重试，也避免把某一台设备的坏档位记到新设备头上。

同理，被系统拒绝的混音器属性也不记成「已下发」：记下来会让同一条属性在之后的换曲里再不被重试。
判定「已受理」与抑制重复下发共用同一份状态（acceptedMixerAttributes），不接受「下发过」与「已受理」两本账。

动态混音端口查询会对「没有输出」的设备给空表（已核实，勿把空表当终局）

getSupportedMixerAttributes 不经 AudioService，而是 AudioManager 直查音频策略的原生接口；Java 层把任何
非 SUCCESS 一律折成空表，所以**空表有两种含义**：厂商没声明动态混音端口，或该设备此刻没有输出（平台按
输出端口应答）。实测同一台 KT02H20：应用未起播时查询得空表，起播后同一设备返回 7 条档位。

故「未声明动态混音端口」只能当作**当下这次问不到**，处理方式是把「声明」当成连接级的事实读一次：

- **问到之前一直重问**（UsbDirectOutput.onOutputEstablished，由音频输出的「音频轨已建立」回调驱动）。
  踩过的坑：开关在未起播时打开 → 空表 → 判定设备不支持 → 随后起播，输出已建成却没人再问，
  直出再也没回来（现象：受支持的源采样率也一直走混音，手动换曲同样无效）。
- **问到非空即认定本次连接的答案已定，此后不再问**（UsbDirectOutput.declaredFormatsFor）。厂商声明的档位
  是设备的固定属性，答案不会变；而查询的应答取决于「本应用此刻在该设备上有没有输出」，所以空表对判定
  毫无信息量、非空的答案则一直有效。只重问而不记住也不行：撤销直出会一并解除路由钉定，此后新起的输出
  不再落在该设备上，查询于是永远得空表（现象：末几首一路系统混音，且日志里连一条候选下发都没有）。

另一处必须成对：路由若在曲中才成立，写出变体不会自己跟上（变体只在音频输出重配点决策），故成色回调里
同时补一次重配（PerDeviceAudioSink.syncRouting，投回音频线程、变体未变则跳过）。少了它，状态会显示
「源格式直出」而音频轨仍以浮点写出——格式与偏好不符，AudioFlinger 静默混音，名不副实。

不再申请位完美：请求不到，请求到了更差（已核实于 frameworks/av 源码，勿再加回试探）

MIXER_BEHAVIOR_BIT_PERFECT 只是一条请求，而且这条请求**注定无效**：setPreferredMixerAttributes 把所请求的
行为并进用于匹配的输出 flags（AudioPolicyManager.cpp:5442 `audio_output_flags_from_mixer_behavior`），
IOProfile::getFlagsCompatibleScore（IOProfile.cpp:226）再要求「请求的每个 flag 都已在 profile 声明里」——
判据本体在 policy.h:312 `audio_output_flags_is_subset`：
`((superset ^ subset) & mustMatchFlags) == NONE && (superset & subset) == subset`，profile 是 superset、请求是 subset。
厂商没在动态端口上写 AUDIO_OUTPUT_FLAG_BIT_PERFECT，任何 profile 都过不了这一关，`profile == nullptr` 即
BAD_VALUE（AudioPolicyManager.cpp:5467）——**「厂商漏标而框架受理」这种可能不存在**，故 UsbDirectOutput 里
那次「先试后回落」的试探已整体删除（日志里那条每次都出现的「位完美请求被拒」也随之消失）。行为由 profile 的
AUDIO_OUTPUT_FLAG_BIT_PERFECT 反推（IOProfile::refreshMixerBehaviors），而国产厂商的 USB 声卡普遍不声明它
（实测已知两台：一台只声明 24 位整型，一台只声明 32 位整型，均只有默认行为）。

就算请求得到，这一档在本应用关心的事上**更差**，三处源码：
1. 位完美档会把**别的应用**的媒体轨吸到同一条输出上：AudioPolicyManager.cpp:1564 对别的 uid 保留偏好条目，
   当且仅当 `info->isBitPerfect() && info->getActiveClientCount() != 0`；随后 getOutputForDevices 按
   `info->getProfile()` 复用我们那条输出（AudioPolicyManager.cpp:1975 起），三等——采样率、声道、编码——
   一律不比。默认行为档下同一处 uid 闸门把条目置空，别人的轨进不来。
2. 别人一进来，旁路混音就没了：BitPerfectThread::getTrackToStreamBitPerfectly_l（Threads.cpp:12036）只在
   「除位完美轨外所有活动轨都被静音」时才直通，否则返回 nullptr、`mIsBitPerfect = false` 退回普通混音；
   而我们无权设置别人那条轨的音量。表现就是「卡顿一下之后两路一起响」，成色却仍显示位完美。
3. BitPerfectThread 本身就是 MixerThread（接受多轨），其 prepareTracks_l 专门处理「多条活动轨」的情形
   （注释：No need to copy bit-perfect data directly to sink buffer given there are multiple tracks active）——
   位完美不是独占，恰恰相反。

因此本应用只申请**默认行为**档（UsbDirectOutput.selectDirectMixer 只取 MIXER_BEHAVIOR_DEFAULT 条目）：
专用输出流照开、按源格式、不重采样，且保持单客户端。平台的混音行为枚举对每个动态输出端口恒有一条默认行为
条目，故只取默认条目不会挑不出档位。成色随之只有两档：源格式直出与系统混音。

余下的差别要说清楚：默认行为档的流仍经混音器（音量、挂在输出上的 effect 都作用），只是采样率与格式与源
一致——不保证样本值一字不变，只保证不被重采样。要样本值也不动，只有 raw USB（自己 claim 接口、内核
snd-usb-audio 解绑），代价是整条 USB Audio Class 输出自管——**该路径已实现**，见文末「USB 独占」一节；
它与本节描述的直出在设备层面互斥，界面按二选一呈现，且**永远不能同时成立**。

（另有一条真正绕开混音的路：AAudio 独占/MMAP，数据直写驱动。它要求 HAL 声明 MMAP 支持，且需要另写一套
输出实现（时钟、位置、欠载都得自管），与 media3 的音频输出体系不兼容，同样不在当前范围内。）

**AAudio 独占在 USB 输出上已实测不成立，勿再投入**（KT02H20 / Xiaomi 2107119DC / Android 14，2026-10-21）：
请求 `EXCLUSIVE` 开流，返回成功但 `getSharingMode()` 是 `SHARED`——被静默降级，连错误码都没有；`framesPerBurst`
882（44.1k 下 20ms）、容量 3492，是 legacy 深缓冲的形状而非 MMAP 的短突发。原因是 AAudio 的独占只走 MMAP，
而 USB 走 legacy USB HAL，不提供 MMAP。请求 `EXCLUSIVE` 却拿到 `SHARED` 时，流虽能发声也不要当作成立——
判据只能是 `sharingMode == EXCLUSIVE` 且 `getHardwareSampleRate()` 等于所求速率，缺一不算。
推论：USB 上绕开混音器只有接管接口自写等时端点一条路（见「USB 独占」一节），故 `SilentKeepAliveOutput`
与动态端口那套不能因「有了 AAudio」而撤。

变体切换的起停只由 play/pause 决定（已核实，勿在 reset 里清掉起停意图）

音频输出的起停状态由渲染器经 AudioSink.play/pause 下发，`reset` 只是资源操作。把 reset 当作「渲染器停了播」
会在播放中切轨时留下死结：reset 之后渲染器仍处于已启动状态（MediaCodecAudioRenderer.onReset 与
MediaCodecRenderer.reset 都不清除其 isStarted），此后不会再下发 play；于是新生效的变体——变体切换按登记的
播放意图接续（PerDeviceAudioSink.switchTo）——不会被启动，轨道位置随之冻结，媒体3 的停滞检测满 10 秒
即以 ERROR_CODE_TIMEOUT（"Player stuck playing with no progress for 10000 ms"）终止播放。
实测：一次直出格式改挂之后即撞上（现象：日志里「变体切换：FLOAT → INT32，保持暂停」，13 秒后播放失败）。

故 PerDeviceAudioSink.reset 只登记释放（outputReleaseRequested）而不动 playRequested，起停一律由
play/pause 决定。

受理混音器属性 ≠ 本应用真的用得上它（已核实，勿以受理为终局）

setPreferredMixerAttributes 的受理只说明设备侧存在匹配的动态输出 profile，**不说明本应用建得起与之
逐字段一致的音频轨、更不说明写得出去**。同一台机（KT02H20，Xiaomi 2107119DC / Android 14）两处都实测过：

- 按默认行为下发「48000Hz/2ch/24 位整型」，系统受理并进入「源格式直出」，随后
  IntPcmAudioSink 建轨抛 UnsupportedOperationException: Cannot create AudioTrack——AOSP 里该裸消息只出自
  Builder.build() 的「原生建轨失败、轨道停在 STATE_UNINITIALIZED」一处（AudioTrack.java:1563-1567），
  不是 Java 参数问题；该异常随 ERROR_CODE_AUDIO_TRACK_INIT_FAILED 终止了整曲播放。
- 另一档 24 位轨**建得起来、写不出去**：轨道建成后 write 返回 AudioTrack.ERROR_INVALID_OPERATION(-3)，
  播放随 ERROR_CODE_AUDIO_TRACK_WRITE_FAILED 终止。该错误码不在媒体3 的可恢复集（只有 ERROR_DEAD_OBJECT
  算可恢复），所以它会直接带走整曲播放，而不是交给渲染器重试。

三条结论：

1. **事前推断拦不住它，也不该去做。** 唯一的判据是真实建轨与真实写出；事前实测的结论取决于当时的现场，
   且探测本身会把设备拖坏（见上条）。
2. **唯一可靠的拦截点是 sink。** 生效变体建不起音频轨、或建起后写不出，都必须逐档降级：
   PerDeviceAudioSink 捕获 InitializationException 与 WriteException（后者只取不可恢复的一支），
   通知直出把该格式记为不可用并改挂下一档，本次缓冲续写；全部用尽才交**可恢复**错误（不以不可恢复错误
   终止播放）。直出是尽力而为，任何一环失败都不该把整曲播放带走。
3. **降级次序由设备声明的档位逐档退让得出，不用固定次序表。** 档位一律取自设备声明的动态混音端口条目
   （UsbDirectOutput.directMixerCandidates：与源同率的在先、同族整数倍的在后，不再按源位深与源采样率另拼
   候选去试探未声明的参数），故次序是「首选那一档 → 被证伪后次选那一档 → 无档位可用即系统混音」。
   固定次序表（曾为 FLOAT → INT16 → INT24 → INT32）做不到这一点：它不知道设备声明了哪些位深。
   位深优先序见 selectDirectMixer/encodingPreference：解码输出为浮点，不得落到 16 位档位——那正是
   「24 位源被写成 16 位」的来路。
   **续试在撤销之前做**：setPreferredMixerAttributes 是覆盖式的，改挂成功即无需撤销，设备也不会被解钉；
   撤销会把设备解钉、成色落回系统混音（免打扰白翻一次），并触发上一条那个「再也回不来」的死结。
   改挂不成才撤销——那条失败格式的偏好此刻仍挂着，不清掉 AudioFlinger 会继续静默混音。

   缓冲区间的处理两边不同，别混：建轨失败发生在对本缓冲的任何读写之前，可直接改交下一个变体；
   写出失败时缓冲可能已被消费（媒体3 的输出实现会就地消费输入缓冲），故统一退回本轮的缓冲起点再重试。
   失败的一方已随切换被释放，它接纳而未播出的数据不会再播出，整块重写才是连续的。
4. **该机的 24 位整型整档不可用，而设备声明的 32 位档位可用**：44100/24 被拒、48000/24 被受理但建轨抛
   异常、96000/24 被受理但写出失败。位深优先序使写出优先取容量更大的档位，故 24 位源在这台机上
   取到的正是 32 位（左移补零，逐位无损），不会再撞上 24 位轨；只有设备在该采样率下**只声明了 24 位**
   时才会用到它，届时它失败一次、记入不可用（UsbDirectOutput.unrealizableFormats，按格式记、换设备即
   清零），无档位可退才回系统混音。

解码输出恒取浮点（已核实，勿再按源位深收窄）

媒体3 只在**恰好**收到 `SINK_FORMAT_SUPPORTED_DIRECTLY` 时才向解码器索取浮点输出
（MediaCodecAudioRenderer 据此设 KEY_PCM_ENCODING），故能力基准报什么，解码输出就取什么。

PerDeviceAudioSink 的能力查询恒按浮点变体回答（PerDeviceAudioSink.getFormatSupport），不随源位深分化：
直出追求按源格式写出，解码统一落在浮点、由写出端按目标位深取整，精度只多不少；而按源位深把 16 位及以下
的源改答「需转换」，只换来一次 16 位解码与随之的又一次补位转换，收益为零，故**不再区分源位深**。

一位曾经的顾虑可以放下：面板的「解码输出」一栏展示的是解码头实际产出的编码，源位深另由容器头读出并经
audioSignalPathFormat 独立展示，两者不因解码恒取浮点而对不上。

起播前仍按容器头读一次位深与声道（MusicPlaybackState.recordSourceBitDepthBeforePlayback，切歌入口与
自动接续两处都调），但这只服务信息条在解码前的展示，与音频输出的申报无关。只读容器头、不读采样率与
比特率，后两项由轨道回调补齐。


同族倍率档：设备不声明源采样率时的直出出口（已核实，勿改成「让系统升采样」）

背景：设备（USB 解码器的动态混音端口）只声明 88.2kHz 而不声明 44.1kHz 时，按「与源同率」筛不出任何档位，
直出整体让位、播放交回系统混音——而系统混音器会把 44.1kHz 重采样到设备当时那档采样率（通常是 48kHz），
那是**跨时钟族**的任意比重采样。做法是给直出多一条候选：取设备声明里**同族整数倍**的那一档
（44.1→88.2、44.1→176.4、48→96…；判据见 sameFamilyMultiple：整除且倍率为 2 的幂，取最小倍率），
由本应用把数据按该倍率补齐后挂上去。同族即时钟同源，设备侧不必再做一次异步转换；整数倍即补出来的样本
不含任意比重采样带来的误差。

这不是「挑最接近条目」的退让——那是拿跨族档位凑合、数据要真的重采样。三条边界：

1. **倍率数据必须由本应用补齐**（SameFamilyUpsampler）。只把偏好设成 88.2 而仍写 44.1 的帧，写出的三项
   与混音器属性不匹配，轨挂不上专用输出流、AudioFlinger 静默混音，「绕开系统重采样」一句也不成立，
   而界面还会显示已直出。
2. **保真只有一条承诺：原样本逐位保留。** 半带结构把偶数相位做成「照抄半程之前那一个」，奇数相位才是插值
   出来的新样本，故这是构造上的保证而不是近似还原（实测影像抑制 -108dB、通带增益误差 4e-6，
   见 SameFamilyUpsampleTest）。代价说清楚：**不是位完美**——输出确实多了样本、DAC 也按倍率跑。
   解码输出的中间态用双精度：浮点与 32 位整型都能被它无损容纳，32 位源不会在这里丢低位。
3. **延迟与收尾成对，倍率变更只能整体重配。** 半带滤波有 48 个源样本（44.1kHz 下约 1.09ms）的固有延迟，
   故曲末必须冲一次尾段（PerDeviceAudioSink.playToEndOfStream → SameFamilyUpsampler.drain），不冲就是丢掉
   最后那一段原样本；曲首则是延迟线未灌满的渐入。降级重挑出的档位若换了倍率（或档位用尽而交回系统混音），
   必须先作废手里的余量再整体重配：余量是旧倍率下的数据，写进新档就是错速率的音频，比丢一段余量严重得多，
   而源缓冲未被消费、渲染器会原样再送一次，数据不丢。

展示口径：音频信息面板的「输出采样率」在直出成立时给**源采样率**（见 AudioInfoCollector.outputSampleRate
的注释）——内容频率与内容一个样本都没变，升采样只改样点密度；设备侧真实的流速率由诊断日志留痕
（输出成色那一条会打印已受理属性的采样率）。成色仍是「源格式直出」，心动模式的互斥判据不变。

落地位置：候选在 UsbDirectOutput.directMixerCandidates 与 selectSameFamilyUpsample；插值在
PerDeviceAudioSink（按倍率放大内层配置、写出前插值、余量握在本层、曲末冲段）。

输出采样率的两层口径（已核实，勿再混谈）

一处反复出现的分歧：说「本应用不协商采样率」还是「采样率跟着设备支持在走」，两者都对——答的是不同的问题。

1. 谁做的调整：本应用不重采样，也不为迁就设备挑采样率。直出档位只有两条来源，都出自设备声明的动态混音
   端口条目：与当前解码格式**同率**的那一条优先，缺席时退到**同族整数倍**那一条（倍率数据由本应用补齐，
   见上条与「同族倍率档」一节）。不做「挑最接近条目」的退让——那是拿跨族档位凑合、数据要真的重采样；
   也不按源位深与源采样率另拼一条去试探设备没声明的参数（那样换来的只是一次被拒，或一条受理了却写不出的
   轨道）。两条都挑不出即整体让位，输出路由与混音器属性一并撤销，播放交回系统混音。
2. 最终落在哪一档：设备侧那条流始终落在设备支持的那一档。同率档成立时输出即源采样率、数据一字不动；
   倍率档成立时设备侧落在同族倍率上（如 88.2kHz），而**内容速率不变**——原样本逐位保留、内容频率不变，
   故面板按内容口径显示源采样率。直出不成立时由系统混音器把源重采样到设备的采样率——
   AudioInfoCollector.outputSampleRate 此时读的是设备的 PROPERTY_OUTPUT_SAMPLE_RATE，
   与源不等即在音频信息面板标为已重采样。

故「动态适应设备」作为结果描述成立，「本应用不协商采样率」作为机制描述也成立；把二者说成互相否定的，都是只读了一层。
副标题取的是结果口径。

系统导航栏（虚拟按键）适配（已核实，勿只留一处）

「虚拟按键压在播放控制按钮上」不是布局写错，而是两件事叠加：三键导航栏默认带一层系统铺的不透明底色，
且 edge-to-edge 下底部偏移被取消、内容默认延伸到导航栏后面。下面几点共同构成适配，删掉任一点都会退回原状：

1. `MainActivity` 在 `enableEdgeToEdge` 之后必须显式 `window.isNavigationBarContrastEnforced = false`。
   只靠 `enableEdgeToEdge` 拿不到全透明导航栏：其默认 `navigationBarStyle` 为 `auto`，而 `auto`
   会打开强制对比度（API 29+ 由 androidx 设 true，API 35+ 平台默认即 true），三键导航栏被铺上不透明底色。
   `auto` 与 `light/dark` 的差别就在这个属性，与传入的 scrim 颜色无关。
2. 首页竖屏与横屏一并全沉浸：`isHomePortraitImmersive` 同样走 `HIDE_ALL`，首页（含在线搜索页、歌单页）
   隐藏状态栏与导航栏两条。沉浸只下发隐藏、不裁剪布局——上滑临时唤出的系统栏以覆盖方式呈现，
   不改变 insets，故界面侧不必为它做避让。
3. 仍显示系统栏的页面（设置/排版/频谱/存储管理/元数据）各自避让导航栏高度，无一处统一兜底：
   滚动页把避让加在滚动容器上（`navigationBarsPadding`，见 `CacheGroups` 原注释）；
   带键盘的页一律取 `WindowInsets.ime.union(navigationBars)`（元数据编辑页）——键盘展开时其高度
   已含导航栏区域，直接叠加会让出两段高度。
4. 首页的避让分两类。搜索页与歌单页列表在沉浸态下取值恒为 0，保留并非冗余：导航栏被外部原因
   显示出来时（独立窗口、切页过渡、ROM 不认隐藏请求）仍能保证底部控件不被压住。
   竖屏播放页的 `bottomClearance` 则取固定留白 `BottomBarClearance`（24dp）与导航栏高度的较大值，
   沉浸态下不为 0 —— 底部留白由该固定值决定，而不是由「屏幕高宽差减去内容高度」的余量决定；
   后者随屏幕尺寸与高宽比漂移，同一套布局在不同机型上会忽高忽低。竖屏播放页的高度分配也不再用
   手工估算的内容高度：封面、歌词组、信息/控制组三组之间由 `Arrangement.SpaceBetween` 分配，
   封面为 `weight(1f, fill = false) + heightIn(max = 全宽正方形)`（保留正方形、窗口过矮时收缩），
   富余空间只落入封面↔歌词、歌词↔歌曲信息两处，把歌词组夹在中间均分，内容高度交由系统实测。
   两个底部弹层（播放列表、音频信息）是例外，不避让导航栏：面板底色
   铺到屏幕底缘，在面板根节点预留这段高度只会在底部留下一条与底色同色、不随内容滚动的色带，
   与「元数据编辑页去掉固定底部内边距」是同类问题；面板自身的底部内边距同理取消，只留左右与顶部。
   播放列表弹层仍避让键盘（`imePadding`）——键盘自身已覆盖导航栏区域，无需再叠加导航栏高度。
5. 图标颜色按「图标底下压着什么」定色：首页是深色封面衍生背景，故固定白色（`HomeScreen` 的 `SideEffect`），
   弹层展开时改回按主题取色；其余页面由 `StatusBarStyleEffect` 统一声明。


播放模式新增枚举值只能追加在末尾（已核实，勿再调整顺序）

`PlayMode` 的序号以 ordinal 落盘（`music_saved_mode` 与播放状态快照的 `mode` 字段各一份），
读取时按 `PlayMode.entries.getOrElse(savedMode)` 还原。**在中间插入新值会让已装机用户保存的序号
整体错位** —— 保存的 1 原意是 RepeatAll，插入后会被解析成它前面那个值。新增模式一律追加在末尾，
心动模式（`Highlight`）即按此追加。

心动模式的片段播放不得计入完整播放（已核实，勿放开）

心动模式播的是 30–45 秒的副歌片段，若照常计入 `recordPlayed`，会同时坏掉两处：

1. 常听（`recentPlayedIds`，3 天内播够 2 次）会把每首都收进来，常听歌单失去意义；
2. `PlaylistSort` 等按播放记录排序的路径随之失真。

故 `recordPlayed` 的两个调用点（`onMediaItemTransition` 与 `STATE_ENDED`）都以
`playMode != PlayMode.Highlight` 为前提。裁剪后片段的结束由播放器按「自然播完」上报，
不加这道闸就会静默计入。


心动模式的片段一律取自持久化表（已核实，勿改回播放时解析）

片段的「算」与「用」必须是分开的两段：

- **算**：`HighlightScanner` 在后台成批扫描全库，结果连同「歌词 + 时长 + 算法版本指纹」由
  `HighlightStore` 落盘。指纹未变不重算；歌词补齐、时长补全或算法升级后指纹改变，自动重扫。
  启动恢复完成、曲库变化、启用心动模式三处触发。歌词此刻取不到的曲目记为 `Unresolved`
  而**不是** `NoChorus` —— 前者只是数据未就绪，据此跳过会让歌词尚未补齐的曲库被整库跳过；
  后者才是真的没有高潮段，只有它才跳过该曲。
- **用**：播放路径只做一次内存查表（`HighlightStore.segmentOf`）。切歌、切模式都不读盘、不定位。

历史上曾在播放路径上按需解析（切歌时读歌词并定位，再逐项替换队列里的 MediaItem 补片段）。
那条路有三个必然的毛病，故不要再改回去：每次切歌都要读盘与计算；片段何时生效取决于歌词何时就绪，
行为不确定（表现为「开了模式却没有片段」）；切换模式要逐项替换队列，队列长时明显卡顿。
还有一个隐蔽的坑：当时的队列一致性判定只比 mediaId 与 URI，看不见裁剪差异，新构建的「带片段的项」
会被判成「队列没变」而跳过装载。现在整队列按片段表一次性重建，`sameQueue` 里保留裁剪区间比较作兜底。

模式切换对当前曲目立即生效（进入自片段起点起播、退出还原到整曲的绝对位置），不是「从下一曲才开始」。
因此落盘的播放位置必须是**整曲的绝对位置**（见 `persistablePositionMs`）：控制器回报的是片段内进度，
直接落盘会让恢复时对不上；恢复由 `mapSavedResumePosition` 换算回片段坐标系，两个方向对称。

片段的收尾一律落在**歌词行的边界**上（见 `HighlightLocator`）：先纳入整个副歌块，
再逐行补到时长下限，上限用「再补一行就会超出」判定，于是最后一行总能唱完，
而不是被 45 秒硬切在半句上。块自身就长过上限时**必须向回收缩**到 45 秒以内，不得把整块原样返回。
收尾另取「下一行起点」与「末字演唱终点」的较大者：逐字歌词的末字可能唱到下一行起点之后，
只认下一行起点会把这一行截断，这正是「末句没唱完就被切走」的成因。



心动模式只做纯歌词分析，不解码音频（已核实，勿改回音频精修）

副歌定位（`HighlightLocator`）只用歌词文本与时间戳，分四步：

- **重复结构**定候选：副歌在歌词上表现为同一批行反复出现，这是 RefraiD、pychorus 一类副歌检测的
  共同前提（副歌是整曲重复次数最多的段落）。只出现一次的行块不成候选；制作信息行（作词/作曲……）
  复用 `LyricFeatures.cleanLyrics` 的同一套前缀判据剔除，避免整段重复的信息行被判成副歌。
- **位置、时长、密度、停顿、结尾权重**给候选打分：首现越晚、时长越贴合 30–45 秒、片段内行越密
  （每秒行数越多）、行间最大间隔越短、越靠近曲末的块越像副歌。
- **取最后一遍完整副歌**：每个候选只收其最后一次能成段的出现 —— 末遍副歌通常是全曲落点，
  且收尾落在歌词行边界上；末遍短到收不出片段时退回上一遍。
- **不取歌词行数少的片段**：候选按片段内行数降序排列，行数相同再比得分，于是「高潮必是 30–45 秒内
  歌词行数最多的一段」直接落在排序首位，稀疏段落自然落选。

**为什么不做音频**：逐曲解码全曲能量（`MediaCodec` 解 PCM、逐帧求响度与高频占比）在整库扫描上
代价偏大，对「有清晰重复副歌」的绝大多数流行歌并不提供额外信息；而把精修推迟到进入模式时才做，
又让片段何时生效依赖扫描时机，行为不确定。改为纯歌词后，扫描只读歌词与时间戳，代价低且与当前
模式无关。为此 `EnergyEnvelope` / `HighlightSelector`（音频兜底与响度谷吸附）连同条目上的
`refined` 标记一并移除；算法版本升至 `v4`，旧结果按指纹整体作废重算。

「有歌词却乱播或漏播」的两个来源据此封死：乱播（把重复的主歌当副歌）靠「行数最多 + 五项打分」纠正；
漏播（歌词无时间轴）判为 `Unresolved` 退回整曲播放，**只有「有可用歌词时间轴 + 确实收不出片段」
才判 `NoChorus` 跳过该曲**，歌词尚未补齐的曲库不会被整库跳过。


心动模式下两套时间坐标不得混用（已核实，勿凭直觉取用）

播放器回报的位置以**片段起点为原点**，而歌词行的时间戳是曲目内的**绝对时间**。
两者只允许在状态层换算，各消费点按用途取值：

- **歌词一律取绝对时间**：`MusicPlaybackState.lyricPositionMs`（= `livePositionMs` + `highlightPositionOffsetMs`）。
  竖屏歌词的跟随锚点、悬浮窗迷你播放器、长按歌词定格编辑目标行，三处都取它。
  它们曾直接读 `livePositionMs`，于是心动模式下整段歌词落后一个片段起点 —— 这就是
  「歌词没跟随片段」的成因。
- **进度条取片段相对时间**：`currentPosition` / `duration` 原样使用，它要的正是「这一段播了多少」。
  显示成 0:12 / 0:40 而非 1:22 / 4:05 是有意的。
- **以歌词行为目标的跳转必须换算**：歌词行给的是绝对时间，`seekTo` 的目标必须是片段坐标系，
  经 `toPlayerPosition` 换算；不换算会落到片段之外被播放器钳到边界。
- **落盘与恢复的坐标**：落盘存整曲绝对位置（`persistablePositionMs`），
  恢复经 `mapSavedResumePosition` 换回片段坐标系。

新增任何读播放位置的界面时，先问一句：我要的是「这一段里的进度」还是「整曲里的时间」。


心动模式与音频直出互斥（判据是取向，不是音量；勿放开）

USB 直出（`AudioOutputMode.FORMAT_LOCKED`）成立时必须退出心动模式，且直出期间不接受再进入：直出为整曲
保真聆听服务，与「把每首裁成 30–45 秒片段」取向相斥。判定以**实际输出成色**为准，不看设置开关 —— 开关
打开而设备不支撑时播放仍走系统混音，此时心动模式照常可用。

（历史：本条原先还列了一条技术理由——「位完美一档绕过系统混音、音量与音效都不生效，片段首尾靠
`Player.volume` 的淡入淡出无从实施」。位完美档已整体移除，本应用用的源格式直出档**按常规链路处理音轨
音量**，那份淡入淡出在其上是生效的；故互斥若日后再议，只剩取向这一条判据，不再有技术障碍。）

片段首尾的淡入淡出靠降低播放器音量实现，不进音频数据

片段由裁剪（`ClippingConfiguration`）切开，首尾都是硬切；`MusicPlaybackState.syncHighlightFadeVolume`
在片段开头把 `Player.volume` 由 0 升到 1、在结尾前由 1 降到 0，掩掉突兀的进出。位置与时长都取控制器
对当前项的回报（裁剪后即以片段为原点）。要点：

- **只对确有片段的曲目生效**：心动模式下没有片段的曲目照常整曲播放，不该被从头淡入到尾。
- **片段播放期间进度轮询加密到 40ms**：200ms 的台阶会让斜坡听成几次跳变；非片段播放仍为 200ms。
- **退出心动模式须即刻把音量复位到 1**：否则淡出末尾的低音量会被整曲播放沿用。

设备没有该编码的解码器时播放无声且不报错（已核实，勿只按解码器初始化回调判断当前解码器）

媒体3 的音频渲染器在设备没有该 mime 的解码器时，把整条音频轨判为不支持
（MediaCodecAudioRenderer.supportsFormat：解码器列表为空即 FORMAT_UNSUPPORTED_SUBTYPE），
ExoPlayer 随之**不选中**该轨——表现为静音走完、播放器不报错，且不会有解码器初始化回调
（`onAudioDecoderInitialized` 不触发）。在《02. 願我可以學會放低你 [ALAC] [16 bit - 44.1 kHz].m4a》
（真身是 MP4 内的 alac 采样描述，16bit/2ch/44100，容器头解析无误）上实测到两个后果：

1. **残留解码器名会顶着当前曲目继续展示**：`MusicPlaybackState.audioDecoderName` 只在解码器初始化回调里
   写入、原先不随切歌清空——上一首 flac 曲目的 `*.flac.decoder` 会一直显示在 ALAC 曲目的音频信息面板上，
   正是「M4A 里的 ALAC 被说成用了 flac 解码器」的来路。现由 `MusicPlaybackService` 的轨道回调按
   「本轨未被选中（无解码器）」与「音频轨换了编码」两种情形清掉，面板改由 `AudioInfoCollector` 给出
   「不可用（本设备不支持 ALAC）」。判据只能是轨道选中状态：解码器名与 mime 都拿不到「本机能解什么」。
2. **无声与「本机解不了」无从区分**，故该情形记一条诊断日志（含 mime 与曲目）并给出提示文案
   （`music_panel_decode_unsupported`）。

ALAC（`audio/alac`）在 AOSP 内**没有**解码器（Codec2 组件与 SoftOMX 的组件表里只有 flac/aac/mp3/opus/…，
Android 官方「支持的媒体格式」表也没有 ALAC 行），能否播放取决于厂商是否提供；本机没有即无法播放，
不能靠容器头解析或换 mux 名字绕过。

自研 ALAC 解码器（补齐 AOSP 缺失的 audio/alac）

上一条记的是「本机没有解码器就只能无声」。现已以自研解码器补齐该格式：接入点取媒体3 官方给出的扩展机制
`DecoderAudioRenderer`（flac/opus 扩展渲染器走的是同一条路），在 `MusicPlaybackService` 的渲染器工厂里
**追加**在默认音频渲染器之后——厂商若自带可用的 `audio/alac` 解码器，媒体3 仍会优先选中它，自研实现只在
系统解不了时接手。解码核心（`data/music/playback/alac/`）不依赖 Android，可脱离设备单测。

三处口径必须与既有的 MediaCodec 路径一致，否则同一首歌在两条路径下会得出两种结论：

1. **解码输出取浮点**，判据与 `MediaCodecAudioRenderer` 相同（接收器能**直接**受理浮点才索取浮点输出）。
   USB 直出按解码输出格式挑混音器属性、音频信息面板按它显示「解码输出」，两处都读这一个值。
2. **渲染器直接构造**（`out.add(AlacAudioRenderer(...))`），不经反射，故不需要额外的 keep 规则。
3. **解码器名**上报的是自有实现（`echotide.alac.decoder`），面板上可直接看出这条轨由谁解。

实现上有两个坑，改这段代码前先看一眼：

- **帧尾的越界读取必须按 0 补齐，不能读相邻帧的字节**：参考实现的比特缓冲一次取 4 字节，帧尾字段的读取
  本就跨过样本末尾。零补齐与「读到下一个样本」都能解出看似合法的结果，但后者会让同一条流随前一条数据的
  不同而解出不同结果（解码输入缓冲被复用时即不成立）。
- **残差余数段在余数小于 2 时少占一位**：这是 ALAC 的编码约定，漏掉这一位会让位流位置逐样本漂移——
  开头几百个样本仍解对，之后整段失真且不报错。

校验方式：与 FFmpeg（不依赖本实现）对同一条曲目的解码结果逐字节比对，全曲 2827 帧 / 46,306,176 字节
零差异；仓库内保留前 14 帧与末帧（唯一自带样本数的分片帧）的逐帧摘要作回归。

容器扩展名不能当格式名（`.m4a` 里的 ALAC 曾被说成有损）

`.m4a` 里的 ALAC 曾显示成 `M4A`，并因此被判成有损、被提示做无损升级——格式名有两处产出，原先都是
「扩展名优先」，而 `.m4a` 只是容器扩展名：里面可能是 AAC，也可能是 ALAC。现由一条共享规则
（`FormatDisplayName.kt`）统一：扩展名能定案就用扩展名，扩展名属于容器时改看 mime，容器头有正面
认定结论时优先用它（`ContainerFormat.codecName`）。

同一族的容器扩展名一并过了一遍，判据是「该容器能否装下无损内容」：

| 扩展名 | 处理 | 理由 |
| --- | --- | --- |
| .m4a / .mp4 / .m4b | 容器头正面认定 ALAC | ISO-BMFF 家族，有声书的 .m4b 同样可能装 ALAC |
| .caf | 不纳入（整体不支持） | media3 无 CAF 提取器，文件连装载都过不了，见下 |
| .m4p / .m4r | 交给 mime | 受保护 AAC 与铃声，内容恒为有损，不值得为其多开一次文件 |
| .ogg/.oga/.mka/.webm/.3gp | 交给 mime | 内容是 Vorbis/Opus/AAC 等有损编码 |

改这段代码前要看一眼的几点：

- **CAF 不做任何处理**：media3 的提取器表里没有 CAF（AC3/AC4/ADTS/AMR/FLAC/FLV/Matroska/MP3/MP4/
  Ogg/PS/TS/WAV/JPEG/AVI/PNG/WebP/BMP/HEIF/AVIF），`caff` 魔数在任何地方都不认识，`.caf` 文件连装载
  都过不了、必然报错。因此不为它写容器解析，也不在格式名规则里给它留位——留着只会让人以为支持它。
- **容器头认定与「值不值得读盘」的门限必须对得上**（见 `isContainerHeaderFormat`）：格式名说不出码流
  的那一族若在门限上被挡下，容器头这条路径就形同虚设。
- 曲库按格式分类（`trackFormatCategory`）仍按扩展名走，有意为之：`.m4a` 作为曲库归类维度是合理的，
  与「这条轨是什么码流」是两件事。

已知未覆盖的两处（都是保守方向的错，不会误报升级）：

- **Ogg 里的 FLAC**：起播后由提取器的 mime（audio/flac）能定案，未播放时的预读只认得出容器，那一格会显示成 OGG。
- **`.wav` 里装 MP3**：位深照 `fmt` 块可信，但码流按扩展名仍算无损。

元数据编辑对「奇葩容器」的适配（大封面 M4A、分片 MP4、Ogg Vorbis）

**一、M4A 的标签读不到，编辑页打开是空表单。** 实测两首歌（`Temporary Test Resources` 里 3000×3000
封面的 ALAC 与 Bilibili 打包的分片 AAC）都是这个形态：`ilst` 下 `covr` 封面排在文本原子**之前**，
封面 1.1MB / 1.8MB，全部文本原子落在 1.2MB / 1.8MB 之后。读取端按「固定 512KB 头窗内解析」，
遍历遇到超出窗口的盒子即判结构不完整并返回，于是整份标签一个字段都读不到——用户把空表单存回去
就等于抹掉文件里的既有标签（内嵌歌词同样读不到）。

修法：`Mp4TagReader` 按盒子头逐层定点下钻（moov → udta → meta → ilst），只读盒子头与命中原子的载荷，
封面原子只读头不读体；读取走滑动窗口（连续小原子共用一次读取，载荷越窗即跳到该原子末尾另起一段），
读取量与封面尺寸无关——实测两首歌分别定点读 96KB / 64KB 即取回全部字段与歌词。

- 写入端本来就能处理这些文件（音频区逐字节不变），出错的是**读取端**：改这类问题要把两条路径的容器口径一起看。
- 歌词原子（`©lyr`）与文本标签同在 `ilst` 下，`MusicEmbeddedLyricReader.readMp4Lyrics` 走同一套定位。

**二、分片 MP4 写入会把尾部整段读进内存。** 搬运判据此前是「**单个**顶层盒子超过 32MB 才拒绝」，
而 DASH 式分片的尾部是成百上千组成对的 moof+mdat，每块都不大、合计可达数百 MB；原实现把它们全部
读进内存（8MB 样本即搬 5.9MB，大文件会被系统回收进程且不产生崩溃日志）。改为按「被 moov 分开的
两侧中**字节更多的一侧**」整段流式搬运，另一侧（只含 ftyp/free 这类小盒子）按字面字节重建。

**三、Ogg Vorbis 的标签此前完全写不进。** 写入分派只认 `OpusHead`，Vorbis 文件整体落到「识别不出容器」
而被拒绝（读取端一直支持它，于是表现为「能读不能写」——在线下载的 .ogg 高品多为 Vorbis）。现在按包头
分辨注释包：Opus 为 `OpusTags`，Vorbis 为 `vorbis`，两者载荷结构一致；差别只在 Vorbis 末尾要多
一个**框架位字节**（0x01），缺它解码器判流损坏。

**CAF 与 AIFF 相关支持已整体移除。** 两者一度都有各自的容器头解析、无损判定、标签读写与读取门限，
但核对 media3 源码后确认：提取器表里既没有 CAF 也没有 AIFF（`extractor` 下只有 wav/flac/mp3/mp4/ogg/
mkv/ts/flv/amr 与各类图片），`caff` 与 `FORM`/`AIFF` 魔数在 media3 里一次都没出现；没有提取器就连媒体项
都装载不了、必然报错，于是两者的容器解析、格式名与无损判定、标签读写、读取门限与测试一并删掉
（CAF 见上表 `.caf` 一行）。

**APE（Monkey's Audio）与 DSD（DSF/DFF）相关支持已整体移除。** 判据与上一条同源：media3 1.11.1 的
提取器表里没有 APE，也没有 DSD/DST，`MAC ` 与 `DSD `/`FRM8` 魔数在任何地方都不认识——这两类文件连
媒体项都装载不了，本应用也没有自研提取器或解码器接手（`playback/alac/` 只有 ALAC 一个自研解码器），
即「能读能写却永远播不出声」。此前为它们保留了一整套旁路设施：容器头解析（`parseApe`/`parseDsf`/
`parseDff`）、标签读写重写（APEv2 条目、DSF 尾部 ID3 与 metadata 指针回填、DSDIFF 的 IFF 块序列）、
内嵌标签/封面/歌词读取、无损判定与容器头读取门限，以及各自的测试夹具。现一并删除：
`ContainerHeaderParser` 只余 FLAC/WAV/ALAC，`LosslessContainerTags` 收敛为 WAV(`RIFF`) 单容器，
`EmbeddedTagBackfill` 的容器扩展名收为 `wav`，`LOSSLESS_FORMATS`/`CONTAINER_HEADER_FORMATS`/
`FORMAT_EXTENSION_NAMES` 不再单列 `APE`/`DSF`/`DFF`；同时 `MusicScanner` 加了一张**曲库白名单**
（`SUPPORTED_AUDIO_EXTENSIONS`，判据同为「本应用能装载播放的容器」），扫描期即排除白名单之外的音频，
这类文件不再进入曲库，按扩展名归类的机制对库内曲目仍不变。两份 README 的 Hi-Res 文案同步收口。

校验方式：两个真实文件走应用自身的读取入口（编辑器回填）与写入路径，产出交 FFmpeg 独立核对——
音频逐包与解码 PCM 摘要一致、封面可解码、标签回读正确；Ogg Vorbis 的产出另核对注释包字段与框架位。


USB 独占：为什么只能"抢掉并自己播"，以及平台层为什么没有别的路（已核实，勿再投入）

**一、独占不是一个可以叠加到直出上的功能，而是另一条输出路径。**

`UsbDeviceConnection.claimInterface(intf, force)` 的 javadoc 是这么写的：`Claims exclusive access to a
UsbInterface`，且 `force true to disconnect kernel driver if necessary`。两句说的是同一件事的两面——独占的
受益人是调用者，而拿到它的手段是断开内核驱动。所以 claim 不是"给设备上锁"，是"把所有权收归自己"。

落到本应用：现有直出走平台音频路径（`setPreferredMixerAttributes` + `setPreferredAudioDevice` →
AudioFlinger → audio HAL → 内核 `snd-usb-audio`），那条链路上该 USB 音频接口**从一开始就被内核驱动持有**，
与有没有在播无关。于是只有两种结果：

- `claimInterface(intf, force = false)` → 失败（内核驱动正持有它），此时什么也没拿到；
- `claimInterface(intf, force = true)` → 成功，但内核驱动被解绑 → HAL 找不到声卡 → **平台路径当场失效**。

没有第三种。想让平台继续播，就必须把接口还给内核驱动；那也就没有独占了。系统自己只在
`com.android.server.usb.UsbDirectMidiDevice` 里这么干过（类注释：*This endpoint will not use ALSA and
opens a UsbDeviceConnection directly*），而它绕开 ALSA 之后用的是 `bulkTransfer`——**MIDI 是批量传输所以
走得通，音频是等时传输所以走不通同一条捷径**（见下一节）。

因此"抢掉设备但不碰背后的流程、让平台走这个流程"这个中间态**不存在**：抢到接口的那一刻平台链路就没了，
抢到之后必须自己播。这也是 UAPP 那类应用的形态。

**二、USB 授权换不来任何独占。**

`UsbHostManager.openDevice` 只有两步：`permissions.checkPermission(...)` → `nativeOpenDevice(deviceAddress)`，
即"校验授权 → 打开 usbfs 节点拿一个 fd"。全程不碰接口、不查"设备是否已被占用"。"权限"在这里的含义是
"允许你打开这个文件"，不是"这个文件归你"；它是逐应用逐设备各发一份的授权
（`UsbUserPermissionManager` 里只有一张 `grantDevicePermission` / `hasPermission` 表，没有任何排他语义）。
推论很硬：哪怕全世界只有本应用持有该设备的授权，平台音频照样工作，别的应用的声音照样能播到这台解码器上
——**因为平台链路走的是 `/dev/snd/`（`UsbAlsaManager` 在设备插入时 `usbDeviceAdded` 操作
`ALSA_DIRECTORY = "/dev/snd/"`），根本不经过 usbfs，也就从不查看谁持有 USB 权限。**

**三、平台层不存在"按应用把别人的输出拦掉"这一格（四条路都走过了）。**

| 思路 | 机制 | 为什么不行 |
|---|---|---|
| 抢焦点 | 焦点栈 + 框架主动执行（fadeOut/duck/mute 都是常量真） | 焦点是**协作式、后请求者胜**：它保证"轮流用"，不能"占住"。且只对进过焦点栈的应用有效，自带原生引擎又不申请焦点的应用完全不受影响 |
| 焦点隔离 | `AudioManager.enterFocusIsolation(uid)` | 要 `MODIFY_AUDIO_SETTINGS_PRIVILEGED` + `audioFocusIsolation` 特性，普通应用拿不到；且它只改**焦点账本**，函数体内没有任何路由调用，也不阻止别人出声 |
| 改路由 | `setPreferredDeviceForStrategy` | `@SystemApi` + `MODIFY_AUDIO_ROUTING`；粒度是**策略**而非应用，而我们要赶的对象与我们同属 MEDIA 策略——把 MEDIA 钉到扬声器等于连自己一起赶走 |
| 虚拟设备 | `VirtualDevice` + `VirtualAudioDevice`（虚拟屏那类做法的正规版） | `createVirtualDevice` 是 `@SystemApi` + `CREATE_VIRTUAL_DEVICE`，仅限持有 CDM 角色的系统应用；且方向相反——它是"我另开隔间圈住我启动的应用"，没法把**别人的**应用塞进去 |
| 回放捕获 | `AudioPlaybackCapture` | 构造入口只有 `Builder(MediaProjection)`，要用户先授权录屏；即便拿到，给的是**副本**，对方照常出声。捕获 ≠ 静音 |
| 全局效果器 | session 0 上挂 effect（`AudioFlinger.cpp` 只查 `MODIFY_AUDIO_SETTINGS`，normal 级） | 门槛意外地低，但天花板也低：官方已标注往 session 0 挂 insert 效果废弃；归属有优先级仲裁（别人能把你踢下来）；只压得住音量、不阻止对方播放，且作用于**这条输出上的全部音频**（可能连自己一起） |
| 全局静音 | `adjustStreamVolume(STREAM_MUSIC, ADJUST_MUTE)` | 公开可用、真静音，但整条 MUSIC 流一起静——别人的没了，我们自己的直出也没了 |
| 截走重路由 | `REMOTE_SUBMIX` | 唯一能"截走并让它不出声"的机制，但要 `CAPTURE_AUDIO_OUTPUT`（signature\|privileged），应用与 shell 都拿不到 |

共同点：Android 的音频模型里**没有"按应用定向静音/拦截"这一格**，因为声卡是全局共享资源。唯一能改变这个
事实的只有"把设备从平台手里拿走"，而那必须自己播——绕回原点。**这四类探索已到边界，勿再投入。**

**四、等时传输必须落在原生层，且零第三方依赖可以做到。**

Java 的 USB 主机 API 不支持等时传输，三处源码注释一致：`UsbConstants.USB_ENDPOINT_XFER_ISOC` 标
"(currently not supported)"、`UsbEndpoint` 标 "Isochronous endpoints are currently unsupported."、
`UsbRequest` 只提 "bulk and interrupt endpoints"。而音频播放**只能**走等时端点。拿 `getFileDescriptor()`
自己发 ioctl 也不行：`Os.ioctlInt` 存在于框架内部（`LocalSocketImpl` 在用），但**不在公开 API**（已用
`javap -classpath $SDK/platforms/android-37.0/android.jar android.system.Os` 核实：110 个公开成员里没有任何
ioctl），而且它只能传一个 int，而 `SUBMITURB`/`REAPURB` 传的是指针。

故分工是：**Kotlin 承担全部外围**（权限、claim、控制请求、描述符解析、样本打包、位置换算），只有"把数据
送进等时端点"这一步落原生。

**为什么不用 libusb**：它是 LGPL-2.1-or-later，一旦作为产物进入 APK 就必须随包附带许可证副本、并保持可
重新链接（独立 `.so`，不能静态链进自己的库）；而本工程 `packaging.resources.excludes` 主动排除
`META-INF/LICENSE*`/`NOTICE*`，`assets/` 也不存在，没有承载这类文本的地方。更根本的是它实际编译 11 个
`.c`、共 **12098 行**。而自写需要的全部 ABI 都已在 NDK 自带的平台头 `linux/usbdevice_fs.h` 里
（`struct usbdevfs_urb`、`USBDEVFS_SUBMITURB`/`REAPURB`/`DISCARDURB`/`GET_SPEED`），
故自写 = 零外来产物、零许可义务，且与平台头随版本同步。

**五、写出侧与平台路径的必然差别（都是等时端点的性质决定的，不是取舍）。**

- **位置只能按"实际送出"估算。** 等时端点没有设备侧的播出台账。原生层在**回收 URB 时**按各包
  `actual_length` 累计"已送出帧数"（`UsbIsoStream::reapLoop`），它就是位置的来源；用提交量会整体偏前
  一个在飞时长（由 `UsbIsoOutput.IN_FLIGHT_TARGET_MS` 折算，两种总线速度下都取到 64ms 及以上），
  表现为曲末判定提前。
- **曲末必须显式排空。** 数据还在环与在飞 URB 里，不 `drain()` 就切歌会把尾巴整段吃掉。
- **音量得自己做。** 绕开混音器即绕开 `AudioManager` 的音量与效果链，软件音量落在打包处
  （`packToSubslot` 的 volume 参数）；**等于 1 时整段缩放不参与**，写出仍是逐位原样。
- **播放/暂停不启停送流。** 停流再起会让设备重新锁一次时钟、产生可闻断续；保持送流则设备始终收到连续的
  包，只是内容为静音（与平台路径上音频轨暂停后仍占着设备时间轴同理）。
- **配置期失败必须抛 `AudioSink.ConfigurationException`，不能抛 `InitializationException`。**
  media3 的 `MediaCodecAudioRenderer.configureSink` **只捕获前者**（其余一概向上抛），用错会把本可优雅
  退回的失败变成崩溃。
- **浮点输入按 24 位计**（`sourceBitDepthOf`）：取 32 会把大量 24 位解码器无谓挡在门外，取 16 则会放过
  会丢低位的搭配。规划判据落在**有效位深** `bitResolution` 而非子槽宽度上。
- **UAC2 的档位不在描述符里**：未声明档位时判为"未知、可用"，权威判定留给运行期问时钟；若把"未声明"
  当成"不支持"，会把所有 UAC2 设备挡在门外。两种 UAC 版本的采样率设置顺序**相反且不可互换**
  （UAC2 在时钟实体上、须在切备用设置**之前**；UAC1 在流端点上、须在**之后**）。

**六、原生层两处易踩的健壮性问题。**

1. **fd 必须自己 dup 一份。** 调用方（`UsbExclusiveDac`）随时可能因拔插或归还而 `connection.close()`，
   内核会立刻把那个编号回收给别的打开操作——继续用原编号发 ioctl 就打到别人的文件上去了。故
   `UsbIsoStream::start` 里 `dup(fd)`，析构时关闭。
2. **提交 URB 失败要判"是否终止"。** 设备消失、连接关闭、接口归还这三类（`ENODEV`/`ESHUTDOWN`/`EBADF`/
   `ENOENT`/`ENXIO`）若不当成终止，环再也腾不出空间，播放线程会**永久阻塞**——表现为整曲卡死，而不是
   安静地失败。

**七、真机上要看什么。**

接管是否成立、设备是否确实从系统音频中消失、归还后能否恢复，都只能在真机上验证。**这一层只留异常留痕、
成功路径不打印**，故判断按下面三条渠道走，不要再去找「已接管」「成色」这类条目：

- **音频信息弹窗「播放链路」组的「音频输出模式」行**：显示「USB 独占」即接管成立；显示「系统混音」说明
  本次退回了平台路径（开关开着、而该设备声明不了本曲格式时即如此）。
- **同一弹窗「当前输出设备」组**：接管期间设备已被内核解绑、平台一次也查不到它，故设备类型、名称、地址、
  支持采样率/编码/通道数这些项只能由接管方给出——**它们能填上，本身就是「设备确实从系统音频中消失」的
  旁证**，与上面那行的独占状态互相印证。
- **日志只看失败**：`UsbExclusiveDac` 的 `接管 <设备> 失败，已回滚` / `归还接口 N 失败` /
  `关闭设备连接失败`；`UsbOutputSink` 的 `独占配置失败，退回平台路径` /
  `独占链路写出失败，退回平台路径`；`UsbAudioCapabilities` 的 `读取 <设备> 的声明能力失败`。

**已知未做的事**（按需再补）：设备被独占期间若用户想临时还给系统，只能关掉开关（关掉即归还，接管本身没有
再细分的"暂停独占"档）；厂商设备兼容性只在一台上实测过（见下节）。

延迟那几行的口径按"本层缓冲"统一（独占路径一样看得到）

独占路径上没有音频轨可读（数据直接交给等时端点），原先面板的延迟几行是空的。现在由写出侧按自己的缓冲
算出（`UsbExclusiveAudioSink.latencyReading`），与平台路径同口径切成两段，但**只有一段能测**：

- **缓冲驻留**：还留在环形缓冲里、尚未被取走的那一段，即「已写出 − 已从环取走」（`framesSent`，装入
  URB 的量）。这是本层唯一可测的一段，也正是缓冲策略能调的那一段，**恒不超过"当前缓冲"那一行报的环
  容量**——两行的容器自此是同一个；
- **缓冲之后那一段**（设备传输与解码器自身的排队）在 usbfs 上没有可查询的口子，一律不产出，
  面板上「输出延迟」那一行随之空着。把"测不到"显示成"很短"比空着更糟。
  已从环取走而尚未送出的**在飞 URB 段**也归这一档：它是主机侧的传输在途量，不是本层缓冲里的存量。

把在飞段从驻留里划出去，是为了让两条路的同名两行读的是同一件事：平台路径那一行的基准是"音频系统已
取走"（播放头），取走后落到混音缓冲与 HAL 的那一段算在"缓冲之后"；独占路径原先取"已送出"（URB 回收）
当基准，于是取走后仍在主机侧在途的那一段也压在驻留上，驻留因此会超过容量——超出的正是这段在途量，
两种总线速度下都是 64ms 及以上（见下文"卡顿"一节）。上界另有兜底：已从环取走的量取自播放线程留下的
快照，可能落后于此刻的已写出量，故按容量封顶（`ringResidentFrames`）；平台路径遇到同类越界是不产出，
这里封顶更贴近真值——缓冲容不下更多，越界只可能来自这份滞后。

面板那几行的措辞随之从"音频轨"改成"缓冲"（`当前缓冲` / `缓冲驻留` / `输出延迟`）：两条路上那一行报的其实
是同一个概念，只是承载它的东西一个是 AudioTrack、一个是环形缓冲。

面板把两个延迟量分行并列、且顺序为**驻留在前**：先看驻留（缓冲策略能调的那一段），再看「缓冲之后」那一段
（`输出延迟`，从缓冲出口即播放头起算，不含驻留）。这两者是链路的两段，不再另给「含缓冲驻留」的全链路一行
——它恒等于两者之和，留在面板上只是让人多数一遍。

**缓冲只报当前容量**：`当前缓冲` 是链路实际授予的容量，平台下限更高、或独占侧环长被在飞段下限抬高时，它会
高于策略申请值（`PlaybackBufferPolicy.TARGET_BUFFER_MS` 换算的时长）——两者一比即可看出策略是被抬升了还是
原样生效，申请值因此不必单列一行。

独占期间音量必须自己施加，且信息面板必须由独占路径自己上报（真机实测，两条都踩过）

实测环境：KT02H20 Hifi Audio（UAC2，控制接口 0、流接口 2，声明 16/24/32 位三档，时钟源 6）。
结论先说：**独占链路本身是通的**——接管成功、播放 53 秒、装入帧数与送出帧数完全相等、欠载 0 次，
说明等时环与反馈跟随在这台设备上工作正常；解码输出是浮点，规划据此选了 24 位槽（3 字节），与
`sourceBitDepthOf` 的口径一致。

**一、音量：本应用的音量由系统掌管，独占绕开混音器后这条链就断了。**

`MusicPlaybackState` 把播放器音量恒定为 1（由系统音量滑杆与音量键掌管响度），于是独占写出侧收到的
`setVolume` 一直是 1.0——**软件音量等于没施加**，链路停在满幅。听感就是"太响且怎么调都没反应"，
而音量键其实在正常改动系统音量、只是够不到这条流。

修法：独占期间响度由应用自持，音量键经媒体会话的远端音量通道交给应用。三点值得记住：

- **档位即事实，0.5 dB/级、共 160 级（满幅 0 dB 至 -80 dB）**（`ExclusiveVolume`）。下界取到 -80 dB：
  写出侧是 15 位定点增益，-96 dB 以下一律乘成 0，再往下加级只是同一个静音的重复档。默认档 -30 dB，
  之后按上次取值恢复，落盘延时合并（长按音量键期间每几十毫秒变一次档，逐档写盘等于把写盘频率挂在
  按键重复率上）。
- **音量键靠"远端音量"接管，系统媒体音量一个数都不动**（`ExclusiveVolumePlayer`）。媒体会话把音量分成
  本地与远端两种，远端即把音量交给应用注册的音量提供者。媒体3 没有公开这个接口，但它会在**播放器自报
  设备音量**时装上提供者（`DeviceInfo.playbackType` 报远端），且该判定在运行期反复读取，故能随路由进出
  随时切换：独占承接写出期间报远端，退回平台路径即报本地、交还系统。长按的连续调节也由这条通道送来，
  无需自己处理按键重复。实测依据见 `androidx.media3.session.MediaSessionLegacyStub` 与
  `PlayerWrapper`（`createVolumeProviderCompat` 只在 `playbackType != LOCAL` 时返回提供者）。
- **实际音量 = 播放器音量 × 应用音量**，两者相乘而不是取其一：心动模式的片段首尾靠播放器音量做淡入
  淡出，独占路径上那次斜坡也得照常生效（等于满幅时打包器整段缩放不参与，写出仍是逐位原样）。

**音量改动在缓冲内逐样本斜坡**（`packToSubslot` 的起止增益参数）：台阶级别的跳变本身未必听成咔哒，
但每块缓冲都来一次就是持续的背景噪声。跳转与重配之后从目标增益直接起步——那处的旧增益属于上一段声音。

早先两版映射都不成立，一并记下以免回头：读系统音量按**平台曲线**换算（`getStreamVolumeDb(..., TYPE_USB_DEVICE)`）
因机而异，多数机型把中低档位压到数十 dB 以下，换算成幅度后整条链路近乎无声；按**档位百分比**线性换算
虽然机型无关，但响度仍取决于系统音量滑杆，独占时系统音量被谁动过就跟着变。

**二、音频信息面板：独占那条路不会自动出现在面板里，得自己上报。**

面板的三行在独占期间全部错位，原因是同一个——它取的全是 `PerDeviceAudioSink` 与平台侧的取值：

- **输出模式**：枚举里原先只有"源格式直出/系统混音"两档，独占用的是另一条路，面板只会显示成系统混音；
- **输出编码 / 浮点写出 / 解码输出**：这三项由音频输出在重配与建轨时上报，而独占不经过
  `PerDeviceAudioSink`，那些回调一次也不发生，面板停在上一曲的取值上；
- **当前输出设备 / 设备类型 / 设备名称**：独占期间设备已从系统音频里消失（内核驱动被解绑），平台侧的
  策略查询一次也查不到它，于是面板落到"扬声器"上——与实际发声的设备完全对不上。

修法：成色由输出路由在实际切换时上报（新增 `AudioOutputMode.EXCLUSIVE`），写出编码由等时输出建立时给出、
释放时清空，解码格式与写出取向由路由代报，设备信息由接管方给出（`UsbExclusiveOutput.deviceInfo()`）。
**判据一律取实际路由而不是"是否已接管"**：开关开着但本曲格式设备声明不了时会退回平台路径，那时真正发声
的是系统那条链路，报解码器同样是与听感对不上。

两条路的设备信息判据不同也值得记一笔：平台那条从 `AudioDeviceInfo` 读，独占这条只能由接管方给出，且
采样率在 UAC2 上还要问一次时钟源（档位不在描述符里）——问过即缓存，查询失败按"读不到"处理，
界面少一行总好过整块面板打不开。

**日志里另有两处值得留意**：一是设备在接管后 33 秒（尚无播放）与播放 53 秒时各报了一次"已拔出"，
从时间点看更像手动拔插（第二次与"太响"这条反馈吻合），不是链路自己掉线；二是独占链路失效后按设计
退回平台路径、播放未中断，这条兜底按预期生效。


独占的暂停与恢复：待播量必须留住，否则媒体3 会把播放状态打回缓冲中（真机踩过）

现象是「暂停指令无法正常生效」。根因不在暂停调用本身，而在**待播判据**：本层的 `hasPendingData()` 是
「已写帧数 > 已送出帧数」，而暂停时环里的数据仍被逐步投出去、补出的静音又被算作「已送出」，待播量
因此一路归零。媒体3 那边是这么用的——

- `MediaCodecAudioRenderer.isReady()` 直接取 `audioSink.hasPendingData()`（没有数据时，只有在
  `hasBeenReady && isStarted && ...` 的宽限期内才暂时算就绪，而暂停时 `isStarted` 已是 false，
  宽限期根本不生效）；
- `ExoPlayerImplInternal.doSomeWork` 里，`STATE_READY` 且 `!renderersAllowPlayback` 即
  `setState(STATE_BUFFERING)` 并 `stopRenderers()`。

于是暂停之后播放状态被打回「缓冲中」且渲染器被停掉，再按播放也起不来。平台路径不存在该问题：
`AudioTrack.pause()` 后播放头不再推进（`AudioTrackPositionTracker.pause()`），
`DefaultAudioSink.hasPendingData()` 是 `writtenFrames > audioOutput.getPositionUs()`，待播量始终保留。

两处改动合起来才对：

1. **暂停时停止从环取数据、改用静音填充**（`UsbIsoStream::setPaused`）。环里攒着的正是「已写出而未
   播出」的部分，保留它待播量才成立。设备侧仍持续收到静音包，故时钟不会被放开、恢复时无需重新锁钟。
2. **「已送出」只计真实音频**。静音补出的帧不是「已播出的内容」，计入会让播放位置越过已写出的量，
   恢复后 `hasPendingData` 会长久为假。

另有一条不可省的防护：写入遇环满且处于暂停时，必须交回已接纳的部分而不是继续阻塞——暂停与恢复都走
调用方那一条线程，阻塞即死锁（原生层的 `write` 因此返回 0 表示「本次一点没接纳」，由上层按「下游已满」
重试，这正是 `AudioSink.handleBuffer` 返回 false 的既定语义）。

启停还要同时下发两条路：未生效一方记下的启停意图，正是它下次被切进来时的初始状态。

USB 接入的系统弹窗只对「有应用认领」的设备出现（真机反馈）

用户期望的是插入解码器时系统弹出「是否交由本应用接管」，而当时只有权限弹窗、没有选择框。原因是缺了
一条清单声明：**系统的选择框只对声明了认领意图的设备出现**。补上两件东西即可——

- `android.hardware.usb.action.USB_DEVICE_ATTACHED` 的意图过滤器；
- 同名的 `<meta-data>` 指向 `res/xml/usb_device_filter.xml`。

这个弹窗由系统发出，不依赖应用进程，所以应用没启动时照样会弹（这正是竞品的表现）。选中本应用后，
系统启动对应的活动**并自动授予该设备的 USB 访问权限**。

过滤器里只声明音频类（`class="1"`）：AOSP `DeviceFilter.matches` 先比设备描述符、再逐个比接口，
故解码器把类别声明在接口上的常见形态（设备类 0、接口类 1）同样命中；范围限定在音频类，插 U 盘与键鼠
时不会来打扰。

**该入口由两个 USB 开关的任一启停（真机反馈）**：清单里的认领声明是静态的，组件一直可用就意味着无论开关
开没开，插上解码器都会弹「用哪个应用打开」。可弹窗换来的授权只有 USB 那两条路用得着，两个开关都关着时它
既无用途，又会被读成「插上就自动开了独占」——原先入口在启动时顺手把独占开关打开，正是这种误读的来源。

做法是把组件状态镜像成开关的取值（`setUsbAttachEntryEnabled`，由 `App` 把独占与直出两条流 `combine`
成「任一开启」后写入）：`android:enabled="false"` 保证全新安装时不参与匹配，开关开启时由应用进程置为
启用。组件停用后其意图过滤器不再参与匹配，系统根本看不到本应用，弹窗自然不出现。

直出也算在内：那份授权本是给独占接管用的，但面板的设备能力只认描述符、读描述符要授权（见下一节）。
代价是直出开着时每次插入都会弹一次系统选择框——换来的是插上即能读到设备的真实档位。

入口自身再按落盘值核一次（开关刚关掉、系统的这次启动已在投递途中时，组件状态来不及改），并且**只把界面
带到前台、不写开关**：要不要启用由用户在设置里决定，插入设备不是替用户改这个决定的时机。

设备能力只认描述符声明的口径，平台 API 报不全（真机反馈）

同一台解码器，平台 API 报的最高只到 32 位，而它实际声明 16/24/32 三档。原因是平台那条约定的只是
**动态混音端口声明的条目**（`AudioManager.getSupportedMixerAttributes`），不是设备声明的全部能力。

故 USB 通路一律改读设备自己的描述符（`UsbAudioCapabilities`）：打开设备拿原始描述符随即关闭，
**刻意不 claim 接口**——接管会解绑内核音频驱动、设备随之从系统音频里消失，而这里只是想把能力读出来，
正在走的平台链路不该受影响（`UsbManager.openDevice` 只校验授权并打开 usbfs 节点，不碰接口归属）。
两条路的信息拼装收在同一个 `usbAudioDeviceInfo` 里，避免同一设备在两处显示成不同能力。

**读描述符要先有 USB 授权，而原先只有独占入口会申请**：只用直出时 `hasPermission` 恒为 false，
`read()` 第一道就返回 null，面板退回平台那两份报不全的值——现象与"直出不支持描述符"一模一样。授权属
交互，故有两个入手处：直出开关打开时申请一次（`UsbAccessRequest`，由 `SettingsViewModel` 发起，此刻用户
已明确表示要走这台解码器），以及插入设备时由系统选择框授予（`UsbAttachActivity`，启停条件已由独占扩到
「直出或独占」）。前者覆盖"先开开关后插设备"，后者覆盖"插着设备再开开关"。

两处设备名来源不同，比对必须归一：音频栈给的是 ALSA 声卡名（带 `USB-Audio - ` 前缀），描述符给的是
iProduct（不带）。`usbProductNameMatches` 剥前缀、去空白、忽略大小写后**要求完全相等**——多台同接时
按包含关系匹配会把「K7」与「K7 Pro」认成同一台，把别人的能力显示在当前设备上，比读不到更糟。

描述符只用于**展示与提示**，不能用来挑直出档位：`setPreferredMixerAttributes` 只受理音频策略里
动态输出 profile 声明的条目，描述符里多出来的档位申请即被拒；即便受理也可能建轨/写出失败（见上文
"受理混音器属性 ≠ 本应用真的用得上它"）。改用它挑档，AudioFlinger 不报错而是静默混音，界面却仍显示
「已直出」。

原生库命名为 `libechotide_usb_iso.so`：`libusb*` 这个前缀会让人读成本工程**刻意不用**的 libusb，
名字上跟着混只会让后来者认错实现来源。

等时输出停机时的 URB 释放竞态：没等内核回收完就释放是 use-after-free（真机闪退的成因）

现象是「独占模式下手动切歌偶发闪退、无崩溃日志、进程直接消失」。根因在原生层的停机路径，与切歌高度相关
——切歌正是 `flush()` → 释放输出 → `stop()` 那一段。两条独立的窗口都会让内存在内核手里时被释放：

1. **回收线程恰在停机窗口投出一个 URB**。`stop()` 设 `running_=false` 后 `discardAll()` 撤在飞 URB，
   但回收线程可能已通过 `running_` 检查、正在 `fillAndSubmit` 里提交——那个 URB 没被撤到，随后 join
   返回、对象析构、URB 的内存被释放，内核在回收时把状态写回已释放的结构体。窗口只有微秒级，故「偶发」。
2. **提交失败判为致命后直接退出回收循环**。旧代码在 `-ENODEV/-ESHUTDOWN` 时 `break`，剩下那些在飞 URB
   永远收不回来，`stop()` 照常 join 并释放——同样踩进 use-after-free。

两处合起来的表现就是：堆被写坏后进程在**无关的**地方崩溃，Java 侧一条日志都留不下。修复分三处：

- **回收改用非阻塞 REAPURBNDELAY + poll 等完成事件**（usbfs 在有待回收 URB 时置 POLLOUT）。用阻塞式
  REAPURB 会在「停机时恰好没有在飞 URB」的情况下永远等下去，停机就卡在 join 上。
- **停机后只回收、不投递，直到在飞数归零才退出**；回收通道已断时标记「放弃」，析构时**故意不释放**
  这批 URB（把内存留在进程里），换取绝不误伤无关内存。停止等待以 200ms 为上限，不无限等。
- `inFlight` 改原子量、`discardAll` 用 `exchange` 避免与回收线程的竞态。

反馈端点同理：提交失败不再 `reset()` 释放，而只置「已作废」——停机路径可能正拿它的指针去撤 URB。

独占会话的跨线程释放：连接关闭后再用就是 use-after-free

`UsbDeviceConnection` 关闭后其方法**不做关闭判定**（源码里没有 `mClosed` 检查，`close()` 直接释放原生
对象并置 `mNativeContext=0`，此后任何 `setInterface`/`controlTransfer` 都撞在已释放的对象上）。而本应用
对同一连接有两处并发使用者：播放线程（就绪流程 `prepareStream` 改采样率、切备用设置）与主线程（音频信息
面板查设备能力，会问一次时钟）。任一线程在 `close()` 之后仍调用它，就是原生层的 use-after-free。

故 `UsbExclusiveDac` 加了一把设备锁：`prepareStream`/`idle`/`declaredCapabilities`/`fileDescriptor` 都在
锁内、`close()` 也在锁内——关闭会等到在飞的那次控制请求结束，随后置位 `closed`，此后的调用一律按失败
返回。`fileDescriptor` 已归还时为 -1，`declaredCapabilities` 为 null（问不了时钟就别报一半）。

面板不再直接碰原生句柄：`latencyReading` 由界面线程调用，而句柄的释放与进入原生层的调用都在播放线程上，
故「已送出帧数」改为播放线程取、界面读缓存快照（`cachedPlayedFrames`），`output`/`writtenFrames`/`closed`
按易变发布。

起播阈值：文档与实现不一致，欠载后的静默段被拖长

`PlaybackBufferPolicy` 的注释写「起播阈值取容量的一半」，实现却返回了**整份目标**（目标时长的帧数）。
`AudioTrack` 的起播阈值同时决定欠载后的恢复：一旦低于它就停、灌到它才重新出声。取整份意味着每次欠载后的
静默段最长可达整个缓冲，听感上就是一次断口。修正为以**实得容量**（`bufferSize / frameSize`）的一半入参
——平台下限更高时实得量大于目标值，阈值跟着实得量走。这只影响直出路径；独占路径的欠载由环形缓冲吸收，
断口长度取决于上层停顿时长，不经过这里。

启动第三方应用、或息屏后解锁进桌面即出现断续（瞬时颤音/抖动）：根因是送流线程被抢占，不在设备侧（已定位，勿再靠调大缓冲解决）

现象：独占路径播放中，从桌面启动**任意**第三方应用即可复现可闻的断续/抖动；**息屏后解锁、进入桌面同样
复现**。两者是同一现场的两个入口——都是外部进程占住 CPU，把本应用的送流那一环饿住。它与
`TARGET_BUFFER_MS` 无关（一度抬到 500ms，复现如故），且既有的三类留痕（欠载次数、少送帧数、URB 以错误
完成）一条都不响。

**这一类的现场判据在面板上：看「缓冲驻留」是满的还是空的。** 驻留接近满却仍在卡 = 数据积在环里送不
出去（本节）；驻留被抽空才卡 = 环被抽干、上游供不上（缓冲时长那一侧）。前几轮缺的正是这一步：既有三类
留痕结构上看不见"数据积着送不出去"，于是每轮都在加缓冲，而缓冲从来不是这里的落点。

根因在原生层送流的节奏上，三处叠加（前两处是首轮定位，第三处是第二轮补上的）：

1. **回收线程跑在默认优先级上**（nice 0）。它在每个 URB 回收时都要立刻补一个上去，截止期就是**一个服务
   间隔**（高速下 1ms），而别的应用启动那一波 CPU 抢占足以让它误期数十毫秒。
2. **在飞段只有 8 个 URB × 8 包**，高速下（8000 包/秒）合起来仅 8ms。在飞段一被送空，设备侧收到的就是
   缺口——等时端点没有重传，缺口即断续。
3. **环形缓冲上那把普通互斥锁会把优先级提升整个吃掉。** 播放线程（写环，nice -16）在**锁内**做 `memcpy`，
   回收线程（取数据）要**同一把锁**，而且是每个包锁一次（`fillAndSubmit` 的 packet 循环）。`std::mutex`
   不是优先级继承锁，nice 也不传递，于是外部抢占只要落在"播放线程正持锁"的那一小段上，优先级更高的回收
   线程就会干等在锁上——这条路上提 nice 换不来任何东西。故第 1 条与它必须一起解：提升只治调度，锁把调度
   让出去就没得治。

为什么既有留痕全都不响，值得记一笔，因为它正是上一轮误判成「设备侧缺陷」的原因：欠载计数只在「取数据时
环是空的」那一刻加一，而环里一直有数据（80ms 的环远盖得住那几十毫秒），只是没人把它送出去；URB 也全部
正常完成，只是**晚了**。**环的深度与调度余量是两件独立的事**：环吸收「上游供不上」，在飞段吸收「送流
线程不跑」——后者只有加在飞段才有效，任何缓冲时长都换不来。据此，上一轮「不在本应用可控范围内」的结论
作废。

修法三处，前两处必须成对——优先级提升只在数据面上没有共享锁时才作数：

- **回收线程提到音频优先级**（原生层 `kReapThreadPriority = -19`，即平台的
  `ANDROID_PRIORITY_URGENT_AUDIO`）。截止期是一个服务间隔的线程只能按音频线程的优先级跑；提升失败
  （进程 nice 下限不允许）不致命，链路退回默认优先级下的脆弱状态。
- **环形缓冲改成单生产者/单消费者无锁环**（`UsbIsoStream` 的 `ringWrite_`/`ringRead_` 两个原子量，获取/
  释放语义同步；播放线程等环空间的那把互斥锁只归它自己用，回收线程腾出空间后只发一次**无锁**通知）。
  这是上面成因 3 的唯一解，不是风格取舍：只要数据面上还留着共享锁，"回收线程的截止期是一个服务间隔"
  就不成立——锁会把它的优先级让给持锁者，而持锁者正是随时会被抢走的那个。
- **在飞段按目标时长折算**（`UsbIsoOutput.IN_FLIGHT_TARGET_MS = 64`，由原生层按真实包率折算成 URB 个数，
  配置的 `MIN_URB_COUNT = 8` 作为下限）：高速下 8ms → 64ms；全速下一个 URB 本就长达 8 个服务间隔，
  下限即 64ms，故两种总线速度由此取齐（原先高速 16ms、全速 64ms 的差别没有依据，只是折算方式带出来的）。
  **代价是同样的输出滞后**：这一段落在「输出延迟」那一档，不计入面板的「缓冲驻留」（见上文
  延迟几行的口径），但曲末排空按它等（`drain()`，原生层 `inFlightUs_`），故曲目之间的衔接会跟着长出这一段。

**为什么是 64ms 而不是 16ms**：本值只由一件事定——要容忍多久的调度误期。首轮取 16ms 是按「启动单个应用」
标定的，而息屏解锁是更重的一波：SystemUI、锁屏、桌面、显示唤醒同时上，CPU 还要从熄屏的降频与离线核状态
往上爬。同一个故障在两处复现，说明按「单个应用」标定的余量本身就选错了基准；64ms 是照这一类现场的量级
取的，并顺带把两种总线速度取齐。**它不是实测出来的上限**——真机上若仍能在更长的误期下复现，该动的是这个
数，而不是缓冲时长。

环长下限随之改为「在飞段的目标时长」（`sampleRate × IN_FLIGHT_TARGET_MS`），不再是原来那个把**包数**当
**帧数**的式子；两个值因此必须一起看——环短于在飞段时播放线程写不进、回收线程也腾不出。

**要量化它，读的是"回收线程两次送流之间的间隔超过在飞段多久"。** 欠载、少送帧数、URB 错误这三项
**结构上看不见它**，这正是它们此前一路空白的原因：把读数记在错的地方，比不记更误导。

据此，调大 `TARGET_BUFFER_MS` 对这类断续无效——这一类的落点是在飞段与回收线程优先级，不在缓冲时长。

**真机上怎么验**：独占路径播放中，息屏放置一会儿再解锁进桌面，听是否仍有断续（启停其他应用那一路也可
同批复核）。复现如故时先看面板的「缓冲驻留」：仍是满的、卡照旧，说明这一侧还没吃住，该动的是
`IN_FLIGHT_TARGET_MS`；变成被抽空，说明问题已经转到上游那一侧，那是缓冲时长的事，与本节的三个成因无关。

**边界：本节结论只覆盖独占路径**（既有留痕也只在它上面）。三个成因都长在这条路的私产上——原生等时层与
它自己的环形缓冲，平台路径上并没有对应的东西。平台直出与系统混音路径上，数据的投递由音频服务按自己的
节奏完成，本应用线程被抢占不会让已写入的那一段停下，故这一套成因不适用于它们；那条路上若同样复现断续，
成因另属一类（设备被系统重配等，见上文「平台层不存在按应用把别人的输出拦掉这一格」），须按新的现场另查，
不要把这套结论套上去。

**但上面那句只说"已写入的那一段不会停"，不等于"这一路免疫抢占"**：本应用的写入线程被长时间饿住时，音频
轨照样会被抽干（面板上正是"驻留被抽空"那一侧的形状），落点是缓冲时长、不是本节。两个方向按「缓冲驻留」
是满是空分开，别把成因张冠李戴。

进程无声消失（闪退却无崩溃日志）的判定口径

原生层的 SIGSEGV/SIGABRT 直接终止进程，Java 侧的未捕获异常处理器接不到，本应用不再自行记录它，tombstone 由
系统照常生成。判定因此走系统侧：`adb shell dumpsys activity exit-info <包名>`（直接给出 reason，如
`crash`/`low-memory`/`anr`）与 logcat 的 `am_kill ... reason=`。两份记录都没有时，多半是系统回收
（LMK / ANR）而非崩溃。

两条输出路的缓冲统一为 80ms

直出（音频轨）与独占（等时环）各有一处缓冲，原先分别取 80ms 与 100ms：两条路不可比，同一台设备上只切换
开关就换一种断流/滞后表现。现在两处都由 `PlaybackBufferPolicy.TARGET_BUFFER_MS = 80` 换算——平台侧经
`targetBufferFrames` 折成字节数（`trackBufferBytes` 供自建音频轨的打包整型变体，`provider` 供媒体3 建轨
的那几个变体），独占侧经同一个 `targetBufferFrames` 折成等时环长度，三个落点由同一个式子给出，不会再各自漂移。

80ms 是这两侧的基准取向：够平掉上游（解码、网络）的偶发停顿，又不把暂停、跳转与起播的等待一并拖长。

- **不能靠媒体3 的默认值代劳**：它对线性 PCM 的默认目标是 500ms，比本值长得多，且只覆盖媒体3 自己建轨的
  变体；`IntPcmAudioSink` 自建音频轨，独占路径完全不经过媒体3，只靠默认值就只剩一处受管，另两处随时会与
  它脱开。
- **本值只管「上游供不上」，管不了「送流线程不跑」**：后者要的是在飞段与线程优先级，见下一节。真机上把
  本值抬到 500ms 而断续复现如故，正是这条的实证——排障时不要再走这条路。
- **独占侧的环另有一条下限**：不得短于在飞段的目标时长（两种总线速度下都是 64ms 及以上，见
  `UsbIsoOutput`）——这是硬不变式而非建议，故两个值必须一起看。
- **代价是滞后**：缓冲里的那一段正是暂停、跳转与起播要等的量；直出路径的起播阈值仍取实得容量的一半，
  故起播要等的是半份缓冲而不是整份。

KT02H20 的类请求只在独占路径下应答（已核实）

这块解码器（31B2:1052，KT02H20 Hifi Audio）的播放端点声明为**自适应、无反馈端点**（报告结构行：
`同步=自适应 反馈=无`），采样率由主机的包节奏决定，UAC2 那条 SET_CUR 采样率对它并非必需——96k 一直正常
正是这个原因，与"设置成功"无关。

设备对类请求的应答有前提。同一台机器、同一时刻，区别只在是不是独占路径：

- **只读路径**（`UsbManager.openDevice` 打开、未 claim、流接口停在 alt 0）：时钟源的 RANGE 与 CUR（一次问满
  98B、先问个数 2B、读当前值 4B）以及特征单元读音量，一律返回 -1；
- **独占路径**（接口已 claim、流接口切到 alt≠0）：时钟档位读得出来，且比平台多一档——面板显示
  `44.1/48/88.2/96/176.4/192/352.8/384 kHz · 设备声明`。

由此两条口径：

1. 报告里 USB 段的「描述符声明: 采样率 未声明」是**只读路径的固有限制**，不是解析缺陷。结构行会逐层摊开
   并给出三次尝试的实际字节数，读到 -1 即设备没应答，不要去改解析。
2. **平台漏报 44.1**：`AudioDeviceInfo` 与动态混音端口都只报 7 档（无 44100），而设备实际支持。故直出
   （源格式档）模式下 44.1k 源无法原生输出，只能走同族倍率（88.2）或交回混音重采样；**独占模式可按 44.1
   原生播放**。

不要为只读路径去 `claimInterface(force = true)`：那会解绑内核驱动、把设备从系统音频里摘掉，代价远大于
一份只读档位。
